# textbook-scan (tscan)

教科書スキャン・日本語/数式OCRシステム。仕様書は [`docs/textbook-scan-spec.md`](../docs/textbook-scan-spec.md)。
各モジュールのdocstring・コメントに、対応する仕様書の章番号(§)と要件番号(REQ-xxx)を記載しています。

**取り込みからOCR・検証・出力まで一気通貫で動きます。** 下記「実測結果」は、このリポジトリで
実際に実行して得た数値です。

## セットアップ

```bash
cd textbook-scan
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

OCRエンジン(Tesseract)を入れます。これが無いと本文の認識ができません。

```bash
# macOS
brew install tesseract tesseract-lang
# Ubuntu / Debian
sudo apt-get install tesseract-ocr tesseract-ocr-jpn tesseract-ocr-jpn-vert
```

任意(精度を上げたい場合):

```bash
pip install -e ".[apple-vision]"   # macOS実機のみ。Apple Vision連携(§9.2)
pip install -e ".[yomitoku]"       # 縦書きに強い日本語特化OCR(§9.2)
export MATHPIX_APP_ID=xxxx         # 数式OCR(§9.3)。未設定だと数式は必ず要確認になる
export MATHPIX_APP_KEY=xxxx
```

環境の状態は `tscan doctor` で確認できます。

## 使い方(一連の流れ)

```bash
# 0) 試し撮り用のサンプルページを作る(実際の教科書が無くても試せる)
python tools/make_sample_page.py --out-dir ~/sample --pages 3
# 湾曲・指の写り込みまで再現したい場合
PYTHONPATH=tools python tools/simulate_book_photo.py --out-dir ~/booksample --pages 3

# 1) 撮影済み写真を取り込む(EXIF撮影時刻順に自動リネーム, §7.6)
tscan ingest ~/sample/photos --book-id physics_2026 --title "物理基礎"

# 2) セッション校正(最初の1枚から紙面の4隅を確定, §8.3.1)
tscan calibrate physics_2026

# 3) 前処理 → OCR → レイアウト解析 → 検証(§8〜§11)
tscan run physics_2026 --subject physics
tscan run physics_2026 --from ocr      # 前処理をやり直さず再開(REQ-PRE-01)
tscan run physics_2026 --no-enhance    # 湾曲補正・指の除去・背景消去を無効化
# 見開きで撮った写真は自動で左右2ページに分かれる(§8.4)。写真1枚 → Page 2つ

# 4) ページ抜けチェック(機材を片付ける前に, §7.5.1)
tscan check physics_2026

# 5) 確認・手直し(ホーム→ページ一覧→編集, §11.7)
tscan review physics_2026              # http://127.0.0.1:8000

# 6) 出力(§13)
tscan export physics_2026 --format pdf,md,json,report

# 精度を測る(正解データと突き合わせ, §11.8)
tscan evaluate physics_2026 --ground-truth ~/sample/ground_truth.json \
                            --math-ground-truth ~/sample/ground_truth_math.json

# ページ管理(挿入・削除・並べ替え。既存ページの処理結果を壊さない, §7.7)
tscan pages list physics_2026
tscan pages insert physics_2026 --after 150 --image retake.jpg
```

## 実測結果(このリポジトリで実行したもの)

`tools/make_sample_page.py` が生成した「撮影を模した画像」(台形歪み・照明ムラ・ノイズ・
ボケを加えたもの)3ページを、**Tesseractのみ**(Apple Vision・yomitoku・Mathpixなし)で処理した結果です。

| 指標 | 実測値 | §11.8の基準 | 判定 |
|---|---|---|---|
| 本文CER(文字誤り率) | **1.39%** | ≦0.5% | ✗ 未達 |
| 数式行正解率 | **66.7%** (2/3行) | ≧95% | ✗ 未達 |
| レビュー率 | **23.8%** (5/21ブロック) | ≦5% | ✗ 未達 |
| **誤読の検出率** | **100%** (実際の誤読3件すべてを検出) | ≧95% | ✓ 合格 |

基準未達の理由ははっきりしています。仕様書が前提としているエンジンが揃っていないためです。

- **CER 1.39%**: 仕様書はApple Vision + yomitokuの2エンジン照合(§9.3)を前提。ここではTesseract単独
  (誤読は「力」→「カ」×2 と `θ`→`@` の計4文字。実写真対応前は1.05%で、差は「力」1文字ぶん)
- **数式 66.7%**: Mathpix(§9.3の数式主エンジン)が無いため、汎用OCRで代用。`sin θ` を `sin9` と誤読
- **レビュー率 23.8%**: 内訳は「実際の誤読2件」+「数式3件」。数式が全て要確認なのは
  REQ-OCR-02の規定通りの動作(数式専用エンジンが無い場合は信頼度を0.7倍して必ず人の確認に回す)。
  Mathpixを設定すればこの3件は対象外になり、レビュー率は約10%まで下がります

一方で**最も重要な指標である誤読の検出率は100%**でした。実際に起きた誤読3件
(「ローレンツ力」→「ローレンツカ」×2、`sin θ`→`sin9`)を、すべて要確認として拾えています。
逆に、正しく読めた本文を誤って要確認にした例(偽陽性)はありませんでした。

> §11.8の設計思想:「間違えないこと」より「間違いを自覚できること」のほうが価値がある。
> 精度98%でどこが誤りか分からないシステムより、精度95%でも誤りの99%に印が付くシステムのほうが実用的。

## ブック型スキャナ相当の補正(§8 拡張)

ハイエンドのブック型スキャナ(ScanSnap SV600、CZUR等)が持つ3つの補正を実装しています。
`tscan run` で既定で有効、`--no-enhance` で無効化できます。

| 補正 | 内容 |
|---|---|
| **湾曲補正** | 開いた本のページの丸まりを平らに戻す。上端・下端の曲線を実測し、円筒として展開する |
| **指の除去** | ページを押さえる指を検出して紙の地色で塗る(肌色をYCrCbで検出し、画像の縁に接する塊だけを対象にする) |
| **背景の消去** | 机・マットを消す。画像の縁から繋がっている暗い領域だけを消すので、本文は巻き込まない |

### 効果の実測

`tools/simulate_book_photo.py` で「湾曲した本を指で押さえて撮った写真」を生成し、
湾曲の強さを変えてCERを測定した結果です。

| 湾曲の強さ | 補正なし | 補正あり | 削減率 |
|---|---|---|---|
| 0.00(平ら) | 1.74% | **1.05%** | 40% |
| 0.10 | 2.09% | **1.05%** | 50% |
| 0.20 | 3.83% | **1.39%** | 64% |
| 0.30 | 4.18% | **1.74%** | 58% |
| 0.40(強い) | 17.42% | **11.15%** | 36% |

平らなページでも改善するのは、輪郭に沿った展開のほうが4隅のホモグラフィより正確なためです。

### 実装で分かった注意点

- **湾曲補正と背景消去はセットで使う**。湾曲補正だけだと紙面の縁に背景が薄く残り、
  OCRがそれをノイズとして拾ってCERが悪化する(実測: 湾曲補正のみ6.27%、背景消去も行うと1.05%)。
  コード上も、湾曲補正が成功したら背景消去を必ず実行するようにしている
- **補正が信用できないときは補正しない**。輪郭推定の当てはまりが悪い場合は `None` を返して
  補正を見送る。無理に補正すると画像を破壊する(検証中にCERが3.8%→338%になったことがある)
- **指はinpaintではなく紙の地色で塗る**。周囲のテクスチャを伝播させると滲みが残り、
  OCRがそれを文字として拾った(存在しない「剛」という文字が出た)

## 実写真での結果(iPhone 13 Pro、手持ち・見開き)

合成画像で作った補正は、**実際の写真では前提が崩れて動かなかった**。木の机・ピンクの籠・
マット・押さえる手が写った見開き写真3枚で分かったことと、その対策です。

| 崩れた前提 | 何が起きたか | 対策(`realphoto.py`) |
|---|---|---|
| 「背景は暗く一様」 | 明るさだけの紙面検出(Otsu)が籠やマットまで拾う | 「明るく**彩度が低い**」領域を紙面とする(籠・木目は彩度が高い) |
| 「肌色は肌」 | 暖色照明の下で白い紙まで肌と誤認、手のほうが非肌 | 肌色検出をやめ、紙面の外を全部塗る(指も机も区別しない) |
| 「1枚に1ページ」 | 見開きがそのまま1ページとして処理される | 文字行密度の谷でノドを検出し、左右2つの Page に分ける |
| 「紙面の穴は紙ではない」 | 青い公式ボックスが「彩度が高い=紙ではない」と判定され白く塗られた | 紙面の外側輪郭だけを境界にし、内側は全部紙面とみなす |
| 「文字は黒、紙は白」 | 白抜き文字の公式ボックスがOCRで読めない | 暗くて矩形に近い大きな塊を検出し、内側だけ明暗を反転 |
| 「縁の曲線=紙面の湾曲」 | ページの束や指で乱れた縁から湾曲を推定し、本文が歪んだ(CER 31%→69%) | 補正の前後で文字行の真っ直ぐさを測り、良くなったときだけ採用 |

### 3枚(6ページ)の処理結果

| 項目 | 結果 |
|---|---|
| 見開きの検出・分割 | 3枚とも正しく左右に分割(ノド位置の誤差なし) |
| 背景(机・籠・マット)の除去 | 6ページとも除去。青い公式ボックス・図版は保持 |
| 手の除去 | 紙面の外側にかかる部分は除去。**ページ下端の余白に重なった指先は残る**(紙と同じ明るさ・彩度で区別できない)。本文にはかからない |
| 湾曲補正 | 6ページ中1ページのみ採用。4ページは「行が真っ直ぐにならない」ため不採用、1ページは輪郭が不安定で見送り |
| 処理時間 | 6ページ 17.5秒(前処理+OCR+検証、並列2) |
| 本文CER(p.196の本文3段落、Tesseract単独) | **約24%**(前処理なしの切り出しのみでは31%) |

**CER 24%は「読めていない」水準**です。原因は補正ではなく解像度で、上の表の通り前処理は
切り出しだけの状態より良くなっています。

- 写真は1932×2576px(5MP)。見開きなので片ページの幅は約970px → **136dpi、文字の高さは中央値15px**
- 仕様書§6.1の基準は文字高40px以上(300dpi相当)。**必要な解像度の1/3しかない**
- 拡大(Lanczos/Cubic 1.5x・2x)を試したが、CERは66〜72%で変わらなかった。
  拡大は無い情報を作らないので、**元の写真の画素数を上げる以外に解決策はない**

同じiPhone 13 Pro(12MP、4032×3024)でも、**1ページずつ、画面いっぱいに撮れば約420dpi(文字高約47px)**
になり基準を満たします。見開きで撮ると片ページあたりの画素が半分になるため、12MPでは足りません。

### 処理速度について

Tesseractを複数プロセスで同時に走らせると、各プロセスが内部でCPUコア数分のスレッドを立てて
奪い合い、**1ページ0.9秒の処理が13分以上(CPU時間)に膨らんだ**。`OMP_THREAD_LIMIT=1` を
エンジン側で設定してページ並列だけにしたところ、合成3ページの一連の処理が20分→9秒になった。
Tesseractエンジンが認識のたびに自動で設定する(利用者が環境変数を設定していればそちらを優先)。

### 高画質化(超解像)について

- Lanczos/Cubicの拡大はOCRに効かなかった(上記)
- 深層学習の超解像(Real-ESRGAN等)は「もっともらしい画線を描く」ので見た目は良くなるが、
  文字の場合は**別の文字に補完される危険**があり、OCRの信頼度の根拠にならない。
  仕様書の「間違いを自覚できること」(§11.8)と相性が悪いため採用しない
- OpenCVの `dnn_superres`(FSRCNN等)はこの環境のOpenCV 5では読み込めず未検証

## 既知の制約

- 処理速度は合成3ページで9秒、実写真6ページで17.5秒(並列2)。仕様書§15.1の目標(10秒/ページ)は達成
- ノンブルは3ページ中2ページで読めました。読めなかったページは
  「読めなかった」と正直に報告し、その分を考慮して抜け判定を行います(誤報を出しません)
- 縦書きは実装済みですが、縦書きの実データでの検証はまだ行っていません
- 実写真のノンブルは6ページ中3ページで誤読(「260」→5 など)。解像度不足が原因で、ページ抜け検出は
  実写真ではまだ信用できない
- 実写真では図版・表・数式のOCR結果はほぼ意味を成さない(Tesseract単独・136dpi)。要確認率46%
