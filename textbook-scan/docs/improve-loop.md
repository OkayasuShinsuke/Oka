# 自動改善ループ(複数エージェントによるループエンジニアリング)

これまで人間とClaudeが会話で回していた
「写真を処理する → 読めていない所を見る → 原因を考える → 直す → 測り直す」を、
**寝ている間も自動で何十回も回す** 仕組みです。

---

## 1. たとえ話: 料理コンテストの予選

| 役 | このループでは | やること |
|---|---|---|
| 試食の審査員 | `tscan bench`(プログラム) | 料理(OCR結果)を正解と比べて点数をつける。**気分で点を変えない** |
| 原因調査係 | サブエージェント `failure-analyst` | まずかった皿を実際に見て「塩が多い」など原因を突き止める |
| 料理人 | サブエージェント `fixer` | 原因を1つだけ直したレシピを作る |
| 監査役 | サブエージェント `auditor` | 「審査員の好みを盗み見て、その皿だけ味を変えていないか」を調べる |
| 予選の関所 | `tools/gate.sh`(プログラム) | 点数が本当に上がったときだけレシピを採用する |

大事なのは、**採否を決めるのがAIではなくプログラム** だという点です。
AIは「この変更は良いはず」ともっともらしい理由をつけて自分の案を通しがちです。
数値で機械的に判定すれば、その甘さが入り込みません。

---

## 2. 全体の流れ

```
 tools/improve_loop.sh run 20
   │
   │  1回ごとに新しい Claude Code を起動して /improve を実行(前の回の思い込みを持ち越さない)
   ▼
 ┌──────────────────────── /improve(1回分)───────────────────────────┐
 │                                                                         │
 │  ① failure-analyst   train の写真を採点し、前処理後の画像を見て          │
 │        │             「なぜ読めなかったか」の仮説を最大3つ出す            │
 │        ▼             (LEDGER.md / NOTES.md で過去の失敗案を避ける)       │
 │  ② 仮説を1つ選ぶ                                                         │
 │        ▼                                                                 │
 │  ③ fixer            その仮説だけを小さく実装し、テストを足して pytest     │
 │        ▼                                                                 │
 │  ④ auditor          ずる(決め打ち・正解の書き写し)がないか監査          │
 │        │  NG ─────────────────────────────┐                             │
 │        ▼ OK                                ▼                             │
 │  ⑤ tools/gate.sh ── 変更範囲 → pytest → train改善? → holdout悪化なし?    │
 │        │                         │                                       │
 │     全部合格                  どれか不合格                                │
 │        ▼                         ▼                                       │
 │   commit + 基準を更新        変更を捨てる                                 │
 │        └──────────┬──────────────┘                                       │
 │                   ▼                                                      │
 │  ⑥ LEDGER.md(成績表)と NOTES.md(次の回へのメモ)に記録                 │
 └─────────────────────────────────────────────────────────────────────────┘
   │
   ▼  次の回へ(5回連続で不合格、または回数上限で終了)
```

### train と holdout(模試と本番)

写真を2つに分けます。

- **train(模試)**: AIが結果を見て、直す手がかりにする写真
- **holdout(本番)**: AIには中身を見せず、合否の最終確認にだけ使う写真

模試の問題だけを丸暗記すると模試の点は上がりますが、本番では通用しません。
同じように、train の写真にだけ効く修正(「この写真は右に3px寄せる」のようなもの)は、
holdout で点が上がらない・下がることで見抜けます。

### 基準のラチェット

合格するたびに train の基準点が今回の点に更新されます。ラチェット(逆回転しない歯車)のように、
**一度良くなった水準より下には戻れません**。
holdout の基準は最初に測った点のまま固定です(毎回更新すると、「少しだけ悪化」が積み重なって
いつの間にか大きく悪くなるため)。

## 3. 準備(最初の1回だけ、30分〜1時間)

### 3.1 採点用フォルダを作って写真を入れる

採点用フォルダはリポジトリの **外** に作ります(写真をgitに入れないため)。

```
~/tscan_bench/
├── photos/
│   ├── iphone/        ← セット名 = 撮影条件。フォルダ名がそのままセット名になる
│   │   ├── IMG_8627.HEIC
│   │   └── ...
│   └── apsc/
│       ├── DSC00016.jpg
│       └── ...
└── manifest.json      ← 次の手順で作る
```

- 撮影条件(カメラ・照明・本)ごとにフォルダを分けます。セットごとに悪化を見張るためです
- **1セット6枚以上、全体で15〜30枚** が目安。少ないと偶然の揺れを改善と見誤ります
- 写真は縮小しない元データで(`docs/mac-setup.md` の 7.1)。ARWはJPEGに変換しておきます

### 3.2 manifest.json のひな形を作る

```bash
cd ~/Oka/textbook-scan && source .venv/bin/activate
python tools/make_manifest.py ~/tscan_bench
```

写真が集められ、セットごとに3枚に1枚が holdout に振り分けられます。

### 3.3 正解の抜粋を書き写す(ここだけ手作業)

各写真について、本文から **3〜5か所、1か所1〜2文** を書き写して `snippets` に入れます。
ページ全文は要りません。

```json
{
  "photos": [
    {
      "file": "photos/iphone/IMG_8627.HEIC",
      "set": "iphone",
      "split": "train",
      "snippets": [
        "ビオ・サバールの法則は，まだ電流が荷電粒子の流れであることも，磁場が動く電荷によって作られることもわからなかった時代に，試行錯誤によって発見されました。",
        "電流が作る磁場の向きは，右ねじの法則で決まります。"
      ]
    }
  ]
}
```

書き方のコツ:

| ポイント | 理由 |
|---|---|
| ページの上・中・下、左右のページから散らして選ぶ | 端だけ読めない、などの失敗を拾うため |
| 本文の地の文を選ぶ。数式・図中の文字・ページ番号は避ける | 数式は別の仕組みで扱うため、ここでは採点しない |
| 全角/半角・空白・改行は気にしなくてよい | 採点前にそろえている(NFKC正規化・空白除去) |
| **一字一句正確に**。迷ったら本の実物を見る | 正解が間違っていると、ループは「間違いに合わせる」方向へ進む |

> ClaudeやChatGPTに写真を貼って書き写してもらうと速いですが、**必ず本と見比べて直してください**。
> 特に似た漢字(誘電体/計電体など)はAIも間違えます。

見本: `docs/bench-manifest.example.json`

### 3.4 ループの作業場所と基準を用意する

```bash
cd ~/Oka/textbook-scan
tools/improve_loop.sh setup
```

これで次のことが行われます。

1. `~/tscan_bench/loop/` に **ループ専用の作業ツリー**(git worktree、ブランチ `improve/loop`)を作る。
   ふだん使っている `~/Oka` には一切触りません
2. その中に専用のPython環境を作る
3. 今のプログラムで train / holdout を採点し、基準点として保存する

> **git worktree とは**: 1つのリポジトリから「別の机」をもう1つ出すような機能です。
> 同じ履歴を共有しながら、別のブランチを別のフォルダで同時に開けます。
> ループが机の上を散らかしても、あなたの机は無事です。

## 4. 回す

### 見張りなしで回す(おすすめ)

```bash
cd ~/Oka/textbook-scan
tools/improve_loop.sh run 20      # 最大20回。5回連続で不合格なら自動で止まる
```

別のターミナルから:

```bash
tools/improve_loop.sh status      # 成績表と、ループが積んだ commit を見る
tools/improve_loop.sh stop        # 今の1回が終わったところで止める
```

1回あたりの目安は **10〜20分**(採点を3〜4回行うため。写真の枚数に比例)。
一晩で20〜40回です。

### 対話しながら1回ずつ回す

```bash
cd ~/tscan_bench/loop/textbook-scan
export TSCAN_BENCH_DIR=~/tscan_bench
claude
```

Claude Code の中で `/improve` と打つと1回分を実行します。途中の様子を見ながら口を挟めます。
`/loop /improve` とすると、Claude が自分で間隔を決めてくり返します。

### 結果を取り込む

ループの成果は `improve/loop` ブランチの commit です。1つずつ「何を直して何点上がったか」が
commit メッセージに書かれています。見て納得できたら、ふだんの作業ツリーに取り込みます。

```bash
cd ~/Oka
git log --oneline claude/textbook-scan-app..improve/loop    # ループが足した commit
git show <commit>                                          # 中身を見る
git merge improve/loop                                     # 良ければ取り込む
```

## 5. 安全装置の一覧

| 心配 | 対策 |
|---|---|
| 偶然の揺れを「改善」と取り違える | 全体で0.5ポイント以上良くならないと不合格(`--min-gain`)。パイプラインは同じ入力なら毎回同じ結果になることを確認済み |
| ある撮影条件で良くなり、別の条件で悪くなる | どれか1セットが1ポイントを超えて悪化したら不合格(`--max-set-loss`) |
| train の写真に合わせた決め打ち | holdout で悪化したら不合格。監査役が差分を読んで決め打ちを止める |
| 正解の文を辞書やコードに書き写す | 監査役が止める。holdout の正解はAIに読ませない設定で起動する |
| テストを消して通す | 既存テストの assert 削除・テストファイル削除を関所が検出して不合格 |
| 採点の仕組みそのものを書き換える | `bench.py` / `evaluate.py` / `tools/` / `.claude/` の変更は関所が不合格にする |
| ふだんの作業を壊す | 専用 worktree の中だけで動き、commit も `improve/loop` ブランチにだけ積む |
| 同じ失敗を何度もくり返す | LEDGER.md(成績表)と NOTES.md(学びのメモ)を毎回読んでから仮説を立てる |
| 無限に回り続ける | 5回連続不合格(`TSCAN_MAX_REJECTS`)か回数上限で止まる |

**限界も書いておきます。** holdout を見せない設定は「ファイルを読む道具で開けない」ようにする
ものなので、Pythonを実行すれば読めてしまいます。指示で禁じ、監査役が確認していますが、完全な
遮断ではありません。ときどき `improve/loop` の commit を人間の目で確認してください。

## 6. 設定(環境変数)

| 変数 | 既定 | 意味 |
|---|---|---|
| `TSCAN_BENCH_DIR` | `~/tscan_bench` | 採点用フォルダ |
| `TSCAN_MAX_REJECTS` | `5` | 連続不合格がこの回数に達したら止める |
| `TSCAN_LOOP_BRANCH` | `improve/loop` | ループが commit を積むブランチ |
| `TSCAN_CLAUDE_FLAGS` | `--permission-mode acceptEdits` | `claude -p` に渡す追加の指定(例: `--model sonnet` を足すと安く回せる) |

## 7. 手で採点だけしたいとき

ループを使わなくても、`tscan bench` は単独で使えます。自分で何かを変えたときの確認に便利です。

```bash
tscan bench --split train                                   # 採点して表を出す
tscan bench --split train --save-baseline                   # 今の点を基準にする
tscan bench --split train --baseline ~/tscan_bench/baseline_train.json   # 基準と比べて判定
tscan bench --split train --keep-images /tmp/look           # 前処理後の画像を残して目で見る
```

判定の意味:

| 判定 | 意味 |
|---|---|
| `accept` | 全体が0.5ポイント以上改善し、どのセットも1ポイントを超えて悪化していない |
| `reject` | どれかのセットが1ポイントを超えて悪化した、または全体が0.5ポイント以上悪化した |
| `neutral` | どちらでもない(揺れの範囲。採用しない) |
| `incomparable` | 使ったOCRエンジンや採点対象の抜粋が基準と違い、比べられない |

> **注意**: Apple Vision の有無で点数は大きく変わります。基準は必ず **ループを回すのと同じMac** で
> 測ってください(違うと `incomparable` になります)。manifest の抜粋を足したり直したりしたときも
> `incomparable` になるので、`tools/improve_loop.sh setup` をもう一度実行して基準を測り直します。

## 8. うまくいかないとき

| 症状 | 対処 |
|---|---|
| `manifest.json がありません` | 3.2 の手順で作る |
| 毎回 `ABORT`(関所を通らずに終了) | `~/tscan_bench/sessions/` のログを見る。許可されていない操作で止まっていることが多い |
| 毎回 `REJECT(train:neutral)` で止まる | 写真が少なく、1枚の改善が0.5ポイントに届いていない可能性。写真と抜粋を増やす |
| `REJECT(holdout:reject)` が続く | train に偏った修正ばかり出ている。train の写真の撮影条件を増やす |
| `claude` が見つからない | Claude Code をインストールしてログインする |
