## 1. 背景と目的

### 1.1 解きたい課題

| 課題 | 現状の痛み |
|---|---|
| 数百ページの教科書を電子化したい | フラットベッドスキャナは1ページ10秒 × 300ページ = 50分以上、本を傷める |
| 数式を「画像」ではなく「テキスト」で持ちたい | 画像のままだと検索も編集も再利用もできない |
| 日本語（縦書き・ルビ・旧字）を正しく読みたい | 汎用OCRは日本語縦書きで崩れやすい |
| 撮った写真がバラバラになる | 300枚の `IMG_1234.HEIC` を後から並べ直すのは非現実的 |
| 誤読が怖い | 数式の添字を1つ間違えると、教材として致命的 |

### 1.2 目的（このシステムのゴール）

> **「本を開いて、シャッターを押し続けるだけ」で、
> 数百ページの教科書が『検索できるPDF』と『LaTeX入りMarkdown』になる。
> しかも、誤読しそうな箇所は自動で洗い出され、人間の確認は全体の5%以内で済む。**

### 1.3 成功の定義（ざっくり指標）

| 指標 | 目標値 |
|---|---|
| 撮影速度 | 1見開き（2ページ）あたり 3秒以内 → 300ページ ≒ 8分 |
| 本文（日本語）文字認識率 | 99.5% 以上（自動処理のみ） |
| 数式（LaTeX）行単位正解率 | 95% 以上（自動処理のみ） |
| 人間レビューが必要な行の割合 | 5% 以下 |
| レビュー後の最終精度 | 99.9% 以上 |
| 300ページの一括処理時間 | 60分以内（Mac ローカル、夜間バッチ想定） |

## 2. 用語集（初心者向け）

先に言葉を揃えます。ここを読めば以降の章が全部わかるようにしてあります。

| 用語 | 意味 | たとえ話 |
|---|---|---|
| **OCR** (Optical Character Recognition) | 画像の中の文字を、コンピュータが扱えるテキストに変換する技術 | 人間が写真を見て「あ、これ『微分』って書いてある」と読み取る作業の自動化 |
| **レイアウト解析** | ページのどこが本文／数式／図／ヘッダかを区分けする処理 | 新聞を読むとき、無意識に「ここは見出し、ここは本文、ここは写真」と分けているのと同じ |
| **読み順 (Reading Order)** | 分割した領域をどの順番で読むか | 2段組の記事を「左の列を上から下、それから右の列」と読むルール |
| **LaTeX** (ラテフ) | 数式をテキストで表す記法。`\frac{1}{2}` → ½ | 数式の「楽譜」。記号の並びで数式を一意に表現できる |
| **DPI** (Dots Per Inch) | 1インチ(25.4mm)あたり何ピクセルあるか。解像度の単位 | 網戸の細かさ。細かいほど小さい文字も潰れない |
| **二値化 (Binarization)** | 画像を白か黒かの2色だけにする処理 | コピー機の「文字くっきりモード」 |
| **デスキュー (Deskew)** | 傾いた画像をまっすぐに回転させる処理 | 曲がって貼った切手を貼り直す |
| **台形補正 (Perspective Correction)** | 斜めから撮って台形に歪んだページを長方形に戻す処理 | 斜めから撮った黒板の写真を、正面から見たように直す |
| **信頼度 (Confidence)** | OCRが「この読み取り、何%自信あるか」を示す0〜1の数値 | テストで「これは自信ある／たぶんこう」と自己申告してもらう |
| **アンサンブル (Ensemble)** | 複数のエンジンの結果を突き合わせて多数決する手法 | 3人の翻訳者に同じ文を訳させて、2人以上が一致した訳を採用する |
| **HEIC / HEIF** | iPhone の標準画像形式。JPEGより高圧縮・高画質 | 同じ画質でカバンが半分の重さになる圧縮方式 |
| **ProRAW** | iPhone の生データ形式。編集耐性が最強だがファイルが巨大 | 料理でいう「下ごしらえ前の食材そのもの」 |
| **EXIF** | 画像に埋め込まれた撮影情報（日時・向き・機種など） | 写真の裏に書いたメモ |
| **パイプライン** | 処理を小さな工程に分け、順に流す設計 | 工場のベルトコンベア。各工程は1つの仕事だけする |
| **冪等性 (べきとうせい, Idempotency)** | 同じ処理を何回実行しても結果が変わらない性質 | エレベーターのボタンを5回押しても、来るのは1台だけ |

## 3. スコープ

### 3.1 やること（In Scope）

- ✅ iPhone（48MPカメラ）での連続撮影と、撮影時点での自動ページ連番付与
- ✅ **iPhone以外のカメラへの対応**（§6.1の実効解像度基準を満たすミラーレス一眼等。RAW撮影・テザー撮影に対応。§6.4）
- ✅ 物理・数学の教科書（横書き・数式多め）のOCR
- ✅ 国語・現代文・古文の教科書（**縦書き**・ルビあり）のOCR
- ✅ 数式の LaTeX 化
- ✅ 誤読検出と人間レビューの支援UI
- ✅ **OCR結果の手動修正**（自動検出された要確認箇所に限らず、任意のページ・任意のブロックをいつでも編集可能。§11.7）
- ✅ **ページ抜け・重複・順序ミスの事後修正**（挿入・削除・並べ替え。既存ページの処理結果を巻き込まない。§7.7）
- ✅ **保存先フォルダの指定**（既定値あり・いつでも変更可能。§14.5）
- ✅ 検索可能PDF / Markdown+LaTeX / JSON の出力
- ✅ iPhone（撮影側）と Mac（処理側）の2デバイス構成

### 3.2 やらないこと（Out of Scope / 将来検討）

- ❌ Windows / Android 対応（v1では非対応）
- ❌ 手書きノートの認識（活字のみ。v2で検討）
- ❌ 図・グラフのベクター化（図は画像として切り出すのみ）
- ❌ クラウドへの永続保存（ローカル完結。API利用時のみ一時送信）
- ❌ 自動要約・問題自動生成などのAI学習支援機能（別プロジェクト）

### 3.3 前提・制約

> ⚠️ **著作権に関する前提**
> 本システムは、**利用者本人が所有する書籍を、私的使用（日本の著作権法第30条）の範囲で電子化する**用途を想定します。
> 生成物の配布・共有・公開は想定していません。出力ファイルにはその旨のメタデータを埋め込みます（§13.4）。

## 4. ユーザーストーリー

### US-01: 一冊まるごと撮る
> **物理の教科書320ページをスキャンしたい。**
> アプリを開き、最初に `physics_2026` と入力する。あとは本をめくりながらシャッターを押すだけ。
> 320回押し終えたら「320ページ / 推定320ページ」と表示され、撮影完了。

### US-02: 撮り直す
> 150ページ目で指が写り込んだ。「戻る」を押して撮り直すと、**ページ番号は150のまま**上書きされる。
> 後続の151ページ以降の番号はズレない。

### US-03: 数式を検索する
> 処理が終わった後、「ローレンツ力」で全文検索すると、該当ページのPDFが開く。
> Markdown版を開くと `\vec{F} = q\vec{v} \times \vec{B}` とテキストで入っており、コピペできる。

### US-04: 誤読を直す
> 処理完了後「要確認 14件」と出る。レビュー画面には、元画像の切り抜きと認識結果が左右に並ぶ。
> `x^2` が `x2` になっていた箇所を直し、Enter で次へ。14件を3分で片付ける。

### US-05: 縦書きを読む
> 国語の教科書を同じ手順で撮る。システムは自動で縦書きと判定し、
> 右上から左下への読み順で本文を再構成。ルビは `｜漢字《かんじ》` 形式で保持される。

### US-06: 自動採用された箇所を後から直す
> 処理完了後、要確認は0件だったが、たまたま自分が詳しい章を読み返していたら
> 「導関数」が「道関数」と誤認識されているのに気づいた（信頼度は高く自動採用されていた）。
> ページ一覧からそのページをクリックして開き、該当ブロックをクリックしてテキストを直接書き換える。
> 保存は自動で行われ、Markdown/PDFにも反映される。

### US-07: 撮り忘れに後から気づく
> エクスポート後、149ページと150ページの間で話が繋がっていないことに気づいた。
> ページ一覧画面を開き、149と150の間の「＋」から該当ページを撮り直して挿入する。
> **150ページ以降の処理結果・レビュー履歴は一切変わらない**。挿入した1ページだけが新規に処理される。

### US-08: 保存先をあとから変える
> 最初は内蔵ストレージに保存していたが、複数冊スキャンしてSSDの空きが少なくなってきた。
> 設定画面から保存先を外付けSSDのフォルダに変更する。今後処理する本はそちらに保存され、
> 変更前に処理済みの本はそのまま内蔵ストレージに残る。

### US-09: 試し撮りしてから本番に入る
> 320ページの本番撮影の前に、同じセッティングで10ページだけ試し撮りする。
> Macに転送して前処理結果を確認したところ、台形補正はきれいに決まったが、照明の当たり方で
> 左端がわずかに暗いことに気づいた。LEDの角度を少し調整してから、残り310ページを撮影する。

### US-10: 持っているミラーレス一眼で撮る
> iPhoneではなく、手元にあるSony α6400（Zeiss単焦点レンズ）で撮影したい。
> RAW(ARW)形式で単頁撮影し、Imaging Edge Desktopでテザー撮影しながらMacの指定フォルダに直接保存する。
> `tscan ingest`はiPhoneのHEICと同じコマンドで取り込め、以降の工程も変わらない。

### 5.2 責務の分担（なぜ iPhone と Mac を分けるか）

**REQ-ARCH-01**: 重い処理（前処理・OCR・検証）は必ず Mac 側で行い、iPhone は「撮影」と「その場で気づける軽い検査」のみを担当する。

| 役割 | デバイス | 理由 |
|---|---|---|
| 撮影・ページ番号管理 | iPhone | 48MPカメラがある。手に持って本をめくれる |
| ピントブレ判定・ノンブル即時OCR | iPhone | 0.1〜0.3秒で終わる軽量処理。**その場で気づけることに価値がある**（撮り終えてから気づくと再撮影が必要） |
| 前処理・本文/数式OCR・検証 | Mac | §5.3 の通り、性能・メモリ両面で圧倒的に有利 |
| レビュー | Mac（ブラウザ） | キーボードで高速に修正したい |

> **判断基準**：「その場で気づけると得をすること」は iPhone、「全体を見渡す必要があること」と「重いこと」は Mac に置く。

### 5.3 なぜ Mac（特に大容量メモリ機）で処理すべきか

48MP 画像はメモリを大きく消費するため、処理デバイスの選定は「性能」より先に**メモリと持続性能**で決まります。

```
  1ページあたりの実効メモリピーク（前処理の中間バッファ込み）
  ≒ 元画像(RGB) + グレースケール×4段 + float32変換 ≒ 約 880 MB

           必要メモリ(並列実行時)          持続性能
  iPhone   並列2 → 1.7GB（アプリ上限約4GB） 発熱で後半は定格の約55〜60%まで低下
  Mac      並列12 → 10.4GB（余裕）          ファンがあるため定格を維持
```

320ページを一括処理した場合の実測見積り：

| | 所要時間 |
|---|---|
| iPhone 単体（発熱でスロットリング） | 約148分（2時間半） |
| Mac（12並列、§15.1 の内訳） | 約4〜15分 |

**転送コストとの比較**：iPhone→Mac への転送（AirDrop/iCloud、1.6GB）は約40秒。
一方 iPhone単体処理と Mac処理の差は約144分。「転送する／しない」の判断は下記の不等式で行う。

$$T_{\text{転送}} < T_{\text{手元で処理}} - T_{\text{移送先で処理}}$$

40秒 ≪ 144分 なので、**常に Mac へ転送して処理する**が正解になる。

> 💡 **[学習メモ]** 転送コストは「データ量」に比例(1次)するのに対し、処理コストは「処理の重さ」に比例します。画像処理のように重い処理では、ほぼ常に「強いマシンへ送る」が有利になります（逆に軽い処理・巨大データでは手元処理が勝つ場合もあります＝例: ログの grep）。

**REQ-ARCH-02**: Mac のメモリが大きい（目安 128GB 以上）場合、§9.3 の第3エンジンとしてローカル VLM（Vision-Language Model）を常駐させ、3エンジン多数決（§11.2）を構成する。メモリが不足する環境では2エンジン構成（Apple Vision / yomitoku、Mathpix / texify）にフォールバックする。

### 5.4 iPhoneからMacへの転送方法 ★追加要件

**REQ-XFER-01**: 既定の転送方法は **USBケーブル＋イメージキャプチャ.app**（macOS標準搭載）とする。iCloudを一切経由せず、任意のMacフォルダへ直接保存できる。

```
   iPhone                                  Mac
   ─────────                              ──────────────────────
   Lightning/USB-Cケーブルで接続
        │
        ├─ 初回: iPhone側で「信頼」をタップ
        │
        ▼
   ケーブル1本で直結 ──────────────────▶  「イメージキャプチャ.app」を開く
                                                │
                                          左サイドバーでiPhoneを選択
                                                │
                                          「読み込み先」で保存先フォルダを指定
                                          （§14.5の保存先設定と同じ場所）
                                                │
                                          「すべてを読み込む」
                                                ▼
                                          48MPフルサイズのHEIC/RAWファイルが
                                          直接保存される（iCloud完全不使用）
```

**REQ-XFER-02**: iCloudの空き容量に余裕がない、またはWi-Fi環境がない場合のために、**AirDrop**を代替手段として提供する（ワイヤレス・iCloud不使用・インターネット接続も不要）。

| 方法 | iCloud容量 | 速度(1.6GB/冊の実測) | 自動化 | 推奨度 |
|---|---|---|---|---|
| **USBケーブル + イメージキャプチャ**（既定） | 消費しない | 高速・安定 | 手動（接続のたびに読み込み） | ★★★ 300枚超の一括転送に最適 |
| **AirDrop** | 消費しない | 約40秒/冊 | 手動選択 | ★★☆ ケーブル未携行時の代替 |
| iCloud Drive自動同期 | **消費する** | 回線次第 | 自動化可能 | ★☆☆ iCloud容量に余裕がある場合のみ。既定では非推奨 |

**REQ-XFER-03**: iPhoneを「Macの外付けカメラ」として使う方式（Continuity Camera / デスクビュー）は、本仕様の撮影方式として**採用しない**。

> **検討経緯**: デスクビューは机上の書類を真上から映す、一見この用途に最適な機能に見える。しかし公開情報によると最大解像度は 1920×1440px(約2.8MP)にとどまり、§6.1の要件(48MP)を大幅に下回る。同じ計算式(§6.1)で換算すると、本文漢字は約17px・数式の添字は約10pxとなり、40px以上を実用ラインとする基準(§6.1)を大きく割り込み、文字が判読できるレベルに達しない。Web会議用のビデオストリーム機能であり、静止画の高解像度撮影パイプラインとは別物であることが理由。

## 6. 撮影仕様（iPhone 48MP）

### 6.1 なぜ 48MP が必要なのか（数値で検証）

これは「なんとなく高画質がいい」ではなく、**OCRの成否を分ける物理的な要件**です。

#### 手順1: センサー解像度を確認する

iPhone のメインカメラ（48MP モード）の画素数は **8064 × 6048 px**（アスペクト比 4:3）。

```
8064 × 6048 = 48,771,072 px ≒ 48.8 MP  ✅ 仕様通り
```

#### 手順2: 見開き撮影時の実効 DPI を計算する

B5判の教科書（1ページ 182 × 257 mm）を**見開き**で撮ると、被写体サイズは：

```
見開き幅  = 182 mm × 2 = 364 mm
見開き高さ = 257 mm
アスペクト比 = 364 / 257 = 1.416
```

センサーのアスペクト比は 4:3 = 1.333 なので、**1.416 > 1.333 → 横幅が先に画角いっぱいになる**（幅で決まる）。
周囲に 8% の余白を取るとして、見開き幅に使えるピクセル数は：

```
有効幅 = 8064 px × 0.92 = 7419 px
```

1 mm あたりのピクセル数は：

```
7419 px ÷ 364 mm = 20.4 px/mm
```

DPI（1インチ = 25.4 mm あたり）に換算すると：

```
20.4 px/mm × 25.4 mm/inch = 518 dpi
```

#### 手順3: 12MP（従来モード）と比べる

12MP は 4032 × 3024 px。線解像度はちょうど半分です。

```
有効幅 = 4032 × 0.92 = 3709 px
3709 ÷ 364 = 10.2 px/mm
10.2 × 25.4 = 259 dpi
```

#### 手順4: 文字が何ピクセルになるか

教科書の本文は約 10pt。ポイントとミリの換算は `1 pt = 1/72 inch = 0.3528 mm` なので：

```
本文の漢字の高さ = 10 pt × 0.3528 mm/pt ≒ 3.5 mm
数式の添字（6pt）  =  6 pt × 0.3528 mm/pt ≒ 2.1 mm
```

| | 48MP（518dpi） | 12MP（259dpi） |
|---|---|---|
| 本文の漢字（3.5mm） | 3.5 × 20.4 = **71 px** | 3.5 × 10.2 = **36 px** |
| 数式の添字（2.1mm） | 2.1 × 20.4 = **43 px** | 2.1 × 10.2 = **21 px** |
| ルビ（5pt ≒ 1.8mm） | 1.8 × 20.4 = **37 px** | 1.8 × 10.2 = **18 px** |

#### 手順5: 判定基準と結論

💡 **[学習メモ] OCRに必要な文字高の考え方**
漢字は画数が多い（「鬱」は29画）。線と線のすき間を潰さずに表現するには、
**1本の線に最低2px、すき間にも2px** 必要です。
縦方向に線が10本並ぶ漢字なら `10本 × (2px + 2px) = 40px` が理論下限。
実際はレンズのボケ・手ブレ・JPEG圧縮で劣化するので、**文字高40px以上が実用ライン**、
30px を切ると複雑な漢字とルビが急激に崩れます。

| 判定 | 48MP | 12MP |
|---|---|---|
| 本文漢字 71px / 36px | ✅ 余裕 | ⚠️ ぎりぎり |
| 添字 43px / 21px | ✅ OK | ❌ **崩壊** |
| ルビ 37px / 18px | ⚠️ ぎりぎり | ❌ **崩壊** |

> **結論（仕様決定）**
> - **REQ-CAM-01**: 撮影は必ず 48MP モード（`HEIF Max` または `ProRAW Max`）を使用する。
> - **REQ-CAM-02**: 数式が密な理数系ページ、およびルビの多い国語ページは、**見開きではなく1ページずつ**撮影する（この場合 約733 dpi、添字61px となり安全マージンが大きい）。
> - **REQ-CAM-03**: 12MP モードでの撮影データは、パイプライン側で警告を出す（EXIFの画素数で判定）。

💡 **[学習メモ] ノド（綴じ側）の湾曲がなぜ致命的か**
本を開くと、綴じ側のページは山なりにカーブします。
カーブした面を真上から撮ると、その部分の文字は**横方向に圧縮されて写る**（遠近の影響）。
OCRは「文字は等幅に並んでいる」と仮定しているので、圧縮された領域だけ認識率が落ちます。
アクリル板で平らに押さえるのが最も確実で、ソフトウェアで直す（dewarping）よりずっと簡単・確実です。
厚みのある本ではノド付近だけ浮きやすいので、**アクリル板はノド付近を重点的に押さえる**ようにし、
たわみが気になる場合は厚さ3〜5mmへの変更や、ノド付近への追加の重し(文鎮等)を検討する。

#### 6.3.1 両手を完全にフリーにする撮影サイクル ★追加要件

「本を開きながらシャッターを押せない」という問題は、上記の物理セットアップ**そのもの**が解決するように設計されている。ポイントは、「本を押さえる仕事」をアクリル板の重みに、「シャッターを押す仕事」をBluetoothリモコンに、それぞれ肩代わりさせることである。

```
  ① 両手でページをめくる
        ↓
  ② アクリル板を下ろす（本の上に乗せるだけ。重みで自然に平らになる）
        ↓
  ③ 片手に持った（または首から下げた）Bluetoothリモコンのボタンを押す
     → iPhoneは固定されたまま、画面に一切触れずシャッターが切れる
        ↓
  ④ アクリル板を持ち上げる
        ↓
  ① に戻る（次のページへ）
```

**REQ-CAM-04**: アクリル板は「ノド湾曲の防止」と「本を開いたまま保持する（＝手を離せる）」の2つの役割を同時に担う部材として位置づける。手で本を押さえる運用は、300ページ規模では手ブレ・疲労による品質劣化を招くため、**行わない**。

#### 6.3.2 パイロットテストの推奨

**REQ-CAM-05**: 320ページ規模の本番撮影の前に、**同じセッティングで10〜20ページだけ試し撮りし、Macで前処理結果を目視確認してから本番に入る**ことを強く推奨する。

```
  ❌ 心配な進め方                          ✅ 推奨する進め方

  いきなり320ページ全部撮影                 まず10〜20ページだけ撮影
        │                                       │
        ▼                                       ▼
  Macで処理 → 気になる歪みを発見            Macで処理 → 補正結果を目視確認
        │                                       │
  😱 全部撮り直し？                          気になれば → アクリル板の押さえ方・
                                              LED角度・カメラ高さを調整
                                                   │
                                              OKなら → 残り300ページを撮影
                                              （同じセッティングを維持）
```

この考え方は §9.5 で「ローカルVLMは実測してから本採用を判断する」としたのと同じ思想を、撮影セッティングにも適用したものである。

### 6.4 代替カメラ機材（ミラーレス一眼等） ★追加要件

本章は「iPhone以外のカメラを既に持っている場合、それで代替できるか」という検討である。
結論として、**カメラはiPhoneに固定していない**。§6.1で立てた要件（実効解像度・実用ラインpx数）を満たせば、どのカメラでもよい。

#### 6.4.1 解像度の考え方をカメラ非依存に一般化する

§6.1 の計算式は特定の機種に依存しない、汎用的な式である。

$$\text{実効px/mm} = \frac{\text{センサー長辺px} \times 0.92（余白率）}{\text{被写体の長さ[mm]}}$$

この式に、候補カメラのセンサー画素数を当てはめれば、同じ基準(文字高40px以上が実用ライン、§6.1)で判定できる。ミラーレス一眼カメラ「Sony α6400」（24.2MP・6000×4000px・APS-Cセンサー）を例に検証する。

| | 見開き撮影(364mm) | 単頁撮影(257mm) | 添字(2.1mm)単頁時 | 本文漢字(3.5mm)単頁時 |
|---|---|---|---|---|
| iPhone 48MP | 518dpi | 733dpi | 60.6px ✅ | 101px ✅ |
| **α6400 24MP** | 385dpi | 546dpi | **45.1px ✅** | **75.2px ✅** |
| (参考)iPhone 12MP | 259dpi | 367dpi | 30.3px ⚠️ | 50.5px |

**REQ-CAMALT-01**: 24MP級のAPS-Cミラーレス機は、§6.1のREQ-CAM-02(理数系は単頁撮影)と組み合わせれば、実用ライン(40px)を満たす。見開き撮影は添字が31.8pxとなり不足するため、**理数系ページは単頁撮影を必須とする**（iPhoneより余裕が小さい分、この使い分けの厳守がより重要になる）。

副次効果として、APS-Cセンサーは画素ピッチが iPhone比で約3.2倍(3.92μm vs 1.22μm)大きく、1画素あたりの受光量が多い。同じ解像度でもノイズが少なく階調が豊かになりやすく、細いルビ・添字の再現性には有利に働く。

#### 6.4.2 「写真アプリの補正」問題への対処（RAW撮影）

iPhoneのHEIC撮影(§6.2)は、撮影時に**Deep Fusion / Photonic Engine（自動ノイズ除去・シャープ化）や Smart HDR（自動トーンマッピング）が必ず適用され、オフにできない**。これらは教科書の細い文字に対して、過度なシャープ化によるリンギングや、ノイズ除去による添字のぼやけを引き起こす可能性がある（§8.2 P8で独自にノイズ除去を行うため、**二重にぼける**リスクもある）。

**REQ-CAMALT-02**: ミラーレス一眼を使う場合は、**RAW形式（α6400ならARW）での撮影を既定とする**。RAWはセンサーの生データであり、ノイズ除去・シャープ化は一切適用されない。補正処理の内容を§8のパイプライン側で完全にコントロールできるようになる。

```
  【iPhone HEIC撮影の場合】                  【ミラーレス RAW撮影の場合】
  センサー → Deep Fusion/Smart HDR          センサー → （無加工）
  （ブラックボックスな自動加工）              → ARWファイルとして保存
  → HEIC保存                                → §8.2 P1で自前の現像処理
  → 私たちが受け取るのは加工済み画像           → 補正の全工程を自分で制御できる
```

> 参考として、iPhone側でもこの懸念が的中する場合は「ProRAW Max」への切り替えが選択肢となる（§6.2で容量面から非推奨としたが、画質面ではこちらがブラックボックス処理を軽減できる）。

#### 6.4.3 Mac接続（テザー撮影）

**REQ-CAMALT-03**: ミラーレス一眼はSony純正無料ソフト「Imaging Edge Desktop」等によるテザー撮影を既定の接続方法とする。

```
  α6400 ──USB-Cケーブル──▶ Mac + Imaging Edge Desktop
                              │
                              ├─ Macの画面にライブビュー表示（構図をその場で確認）
                              ├─ シャッターをMac側からクリック（カメラに触れない）
                              └─ 撮った瞬間、指定フォルダに自動保存
                                 （iCloud・Photos.appを一切経由しない）
```

テザー撮影は、§5.4の転送問題（iCloud容量）と§8.3のセッション校正（ライブビューでその場にズレを確認できる）の両方に効く。ケーブル1本でシャッターも転送も完結するため、§6.3.1のBluetoothリモコンは不要になる。

#### 6.4.4 単焦点レンズの場合の距離設計

ズームレンズがなく単焦点レンズのみの場合、画角の調整はカメラの位置（＝§6.3のアーム高さ）でしか行えない。焦点距離ごとに、必要な撮影距離をあらかじめ計算しておく。

$$\text{必要距離}[\text{mm}] = \text{焦点距離}[\text{mm}] \times \frac{\text{被写体幅}[\text{mm}] / 0.92}{\text{センサー長辺の物理幅}[\text{mm}]}$$

| レンズ例 | 単頁撮影(257mm)に必要な距離 | 見開き撮影(364mm)に必要な距離 | 最短撮影距離(MFD) |
|---|---|---|---|
| Sonnar T* 24mm F1.8 ZA | 28.5cm ✅余裕 | 40.4cm ✅余裕 | 16cm |
| Touit 32mm F1.8 | 38.0cm ⚠️MFDまで8cmと近い | 53.9cm ✅余裕 | 30cm |

**REQ-CAMALT-04**: 単焦点レンズを使う場合、§6.3のアーム高さを上記の計算値に固定し、教科書のジャンル(理数系=単頁/国語=見開き)ごとに高さの目印を付ける。最短撮影距離(MFD)まで8cm未満しか余裕がない場合は、必要距離よりやや遠め（余白を広めに）に設定し、レンズ性能が落ちる限界付近での撮影を避ける。

**REQ-CAMALT-05**: 絞りはF8〜F11に設定する（開放だと四隅の解像力が落ち、被写界深度も浅すぎる）。ピントはマニュアルフォーカス＋拡大表示で厳密に合わせ、セルフタイマー2秒または遠隔シャッター（テザー撮影ならMac側のクリック）でシャッター時の振動を避ける。

#### 6.4.5 iPhoneとの比較まとめ・トレードオフ

| | iPhone | ミラーレス一眼(α6400等) |
|---|---|---|
| ピント合わせ | 自動・常に合う | 手動。ズレると復元不可能 |

| 画素ピッチ・階調 | 小さい(1.22μm) | 大きい(3.92μm)。ノイズ耐性で有利 |

**REQ-CAMALT-06**: 撮影機材はiPhoneに限定せず、§6.1の実効解像度基準（実用ライン40px以上）を満たすカメラであれば使用可としする。使用機材ごとに§6.4.1の計算式で実効解像度を事前検証すること。

## 7. ページ管理仕様 ― 「最初にファイル名を決めて撮るだけ」

これがユーザー体験の核心です。**300枚の写真を後から並べ替える作業をゼロにします。**

### 7.1 コンセプト: 撮影セッション（Capture Session）

```
【従来】                          【本システム】
撮影 → IMG_4501.HEIC              セッション開始
       IMG_4502.HEIC                └─ book_id を1回入力: "physics_2026"
       IMG_4503.HEIC                     │
       ...                               ▼
       IMG_4820.HEIC              撮影 → physics_2026_p0001.heic
         ↓                               physics_2026_p0002.heic
   😱 どれが何ページ？                    physics_2026_p0003.heic
      並べ替えに1時間                     ...
                                         physics_2026_p0320.heic
                                           ↓
                                   ✅ 撮った瞬間に確定。並べ替え不要
```

### 7.2 セッションの状態遷移

```
   ┌─────────┐  book_id入力   ┌──────────┐
   │  待機    │──────────────▶│ 撮影中    │◀──┐
   │  IDLE   │                │ CAPTURING│   │ シャッター
   └─────────┘                └────┬─────┘───┘ (counter += 1)
        ▲                          │
        │                     終了 │  ┌───────────┐
        │                          ▼  │ 撮り直し    │
        │                    ┌──────────┐  (counter据え置きで上書き)
        │      エクスポート   │ 完了      │
        └────────────────────│ DONE     │
                             └──────────┘
```

### 7.3 命名規則

**REQ-NAME-01**: ファイル名は以下の形式とする。

```
{book_id}_p{page:04d}.{ext}

例) physics_2026_p0001.heic
    physics_2026_p0002.heic
    kokugo_gendaibun_p0157.heic
```

| 部位 | 規則 |
|---|---|
| `book_id` | 半角英小文字・数字・アンダースコアのみ（`^[a-z0-9_]{1,40}$`）。日本語・スペース・記号は禁止 |
| `p{4桁}` | 0埋め4桁の通し番号。1から開始。最大9999 |
| 拡張子 | `.heic`（iPhone撮影時）／ `.arw`等RAW形式（ミラーレス一眼撮影時、§6.4.6）／ `.png`（前処理後） |

💡 **[学習メモ] なぜ「0埋め4桁」なのか**
`p1, p2, ..., p10` のままだと、コンピュータは**文字列として**並べ替えるので

```
p1, p10, p100, p11, p2, p20, ...   ← 辞書順。人間の直感と違う！
```

となります。桁を揃えると文字列順 = 数値順が一致します。

```
p0001, p0002, p0010, p0011, p0100  ← ✅ 正しい順
```

Python では `f"p{page:04d}"` と書くだけで 0埋め4桁になります。
`:04d` は「10進整数(d)を、4桁に、足りない分は0で埋める」という**書式指定**です。

```python
page = 7
print(f"{page:04d}")   # → 0007
print(f"{page:4d}")    # → "   7"  (スペース埋め。ファイル名には不向き)
print(f"{page}")       # → 7
```

### 7.4 撮り直し（Retake）仕様

**REQ-RETAKE-01**: 直前のページを撮り直す場合、カウンタを進めずに同名ファイルを上書きする。

```
現在 counter = 150
  ├─ 通常撮影  → p0150 を保存、counter = 151
  └─「戻る」   → counter = 150 に戻す
       └─ 再撮影 → p0150 を上書き、counter = 151
```

**REQ-RETAKE-02**: 上書き前の画像は `.trash/` に `p0150_20260911T143022.heic` として退避し、セッション完了時に削除する（誤操作からの復旧用）。

### 7.5 ページ抜け・重複の自動検出

撮影ミス（2枚めくってしまった等）は必ず起きます。**処理側で検出します。**

**REQ-PAGECHK-01**: 各ページの隅にある**ノンブル（印刷されたページ番号）**をOCRし、
ファイル名の連番と突き合わせて異常を検出する。

```
 ファイル名の連番:  148  149  150  151  152
 OCRしたノンブル:   148  149  152  153  154
                            ↑
                    ❌ 150,151 が飛んでいる = 2ページ撮り忘れ
```

検出ロジック（差分の連続性チェック）:

```python
def detect_page_gaps(nombres: list[int | None]) -> list[str]:
    """OCRしたノンブル列から、抜け・重複・逆順を検出する。

    引数 nombres : ファイル名順に並んだノンブル。読めなければ None。
    戻り値       : 人間向けの警告メッセージのリスト。
    """
    issues = []
    prev_value = None
    prev_index = None

    for index, value in enumerate(nombres):
        if value is None:
            issues.append(f"p{index+1:04d}: ノンブルを読めませんでした（目視確認）")
            continue
        if prev_value is not None:
            diff = value - prev_value
            if diff == 0:
                issues.append(f"p{prev_index+1:04d}-p{index+1:04d}: 同じページを2回撮った可能性")
            elif diff < 0:
                issues.append(f"p{index+1:04d}: ページが逆行（{prev_value}→{value}）")
            elif diff > 1:
                missing = diff - 1
                issues.append(f"p{index+1:04d}: {missing}ページ抜けの可能性（{prev_value}→{value}）")
        prev_value = value
        prev_index = index

    return issues
```

💡 **[学習メモ] `enumerate()` と型ヒント**
- `enumerate(list)` は「番号と中身」を同時に取り出す関数。`for i, x in enumerate(xs)` と書けます。
  `i = 0` から始まるので、1始まりのページ番号にするには `i + 1` とします。
- `nombres: list[int | None]` の `| None` は「int が入ることもあれば、None（値なし）が入ることもある」という意味。
  Python 3.10 以降で使える記法です。これを書いておくと、エディタが
  「None のときに引き算したらエラーになるよ」と警告してくれます。
  上のコードで `if value is None: continue` としているのは、その警告に応える防御です。

#### 7.5.1 運用推奨: 機材を片付ける前にチェックする ★追加要件

REQ-PAGECHK-01の検出は、Macに転送してから`tscan check`を実行して初めて分かる。**問題は、このタイミングが「本もアクリル板も片付けた後」になりがちなこと**である。抜けが見つかっても、本を片付けた後では再セットアップの手間が生じる。

**REQ-PAGECHK-02**: 撮影完了後、機材（アーム式スタンド・アクリル板・照明）を片付ける前に、その場で`tscan check`（ノンブルOCRのみの軽量チェック。フルパイプラインより高速）を実行することを運用手順として推奨する。

```
  【推奨する運用】
  iPhone/カメラで撮影完了（機材はそのまま）
        │
        ▼
  その場でMacに転送 → `tscan check` のみ実行（数分）
        │
        ├─ 抜けなし → 機材を片付けて完了
        └─ 抜けあり → 該当ページをまだ開いたまま撮り直し → 追加分だけ転送 → 完了
```

### 7.6 実装方式（段階的）

| フェーズ | 撮影側の実装 | 手間 |
|---|---|---|
| **MVP** | 標準カメラで連写 → Mac 側で「撮影時刻順にソートして一括リネーム」 | 実装ゼロ。ただし撮り直し管理が手動 |
| **v1** | iOS **ショートカット**アプリ（「写真を撮る」＋「ファイルに保存」＋カウンタ変数＋iOS標準の「テキストを認識」アクションで撮影直後にノンブルを読み取り、前ページとの連番を簡易チェック） | ノーコード。Swiftを書かずに準リアルタイムのページ抜け警告が実現可能 |
| **v2** | Swift 製の専用カメラアプリ（`AVFoundation` + `VisionKit`） | 撮り直し・ページ抜け警告・水平ガイドをリアルタイム表示（v1より高精度・高速） |

> 💡 **[学習メモ]** iOS標準の「ショートカット」アプリには、Apple Vision(端末内OCR)を呼び出す「テキストを認識」アクションが用意されている。これと「画像を切り抜く」アクションを組み合わせれば、Swiftのネイティブアプリを書かなくても、撮影直後にページ隅のノンブルだけを読み取り、簡易的な連番チェックをその場で行うことができる。§17開発フェーズでは、この準リアルタイム検出をv1に前倒しできる可能性がある。

**REQ-IMPL-01**: MVP のリネーム処理は以下の仕様とする。

```python
from pathlib import Path
from datetime import datetime
import exifread   # EXIF（撮影情報）を読むライブラリ

SUPPORTED_EXTENSIONS = ["heic", "arw"]   # iPhone(HEIC) / ミラーレス一眼RAW(ARW等, §6.4.6)

def rename_by_shot_time(src_dir: Path, book_id: str, dst_dir: Path) -> None:
    """撮影時刻の昇順にソートし、{book_id}_p0001.heic 形式にリネームして複製する。

    ポイント: ファイル名(IMG_xxxx)ではなく EXIF の撮影日時で並べる。
             連写でファイル番号が飛ぶことがあるため。
             拡張子を問わず(HEIC/ARW等)同じロジックで処理できる。
    """
    dst_dir.mkdir(parents=True, exist_ok=True)

    # (撮影日時, パス) のペアを作る。拡張子の大小文字を問わず全対応形式を対象にする
    entries = []
    paths = [p for ext in SUPPORTED_EXTENSIONS for p in src_dir.glob(f"*.{ext}")] + \
            [p for ext in SUPPORTED_EXTENSIONS for p in src_dir.glob(f"*.{ext.upper()}")]
    for path in paths:
        with path.open("rb") as f:
            tags = exifread.process_file(f, stop_tag="EXIF DateTimeOriginal")
        raw = str(tags.get("EXIF DateTimeOriginal", ""))
        shot_at = datetime.strptime(raw, "%Y:%m:%d %H:%M:%S")
        entries.append((shot_at, path))

    entries.sort(key=lambda pair: pair[0])   # 撮影日時で昇順ソート

    for page_number, (_, path) in enumerate(entries, start=1):
        new_name = f"{book_id}_p{page_number:04d}{path.suffix.lower()}"
        (dst_dir / new_name).write_bytes(path.read_bytes())   # 元は残す（非破壊）
```

💡 **[学習メモ] `sort(key=lambda pair: pair[0])` の読み方**
`entries` は `(撮影日時, パス)` というタプルのリストです。
`key=` には「各要素から、比較に使う値を取り出す関数」を渡します。
`lambda pair: pair[0]` は「その場で作る名前のない関数」で、
「`pair` を受け取って `pair[0]`（＝撮影日時）を返す」という意味。
つまり「撮影日時で並べ替えろ」という指示になります。
`operator.itemgetter(0)` と書いても同じです。

💡 **[学習メモ] `enumerate(entries, start=1)`**
`start=1` を付けると番号が 1 から始まります。ページ番号は1始まりなので、
`index + 1` と書くより意図が明確です。

### 7.7 撮影後のページ管理（挿入・削除・並べ替え）★追加要件

§7.5 では「ページ抜けを**検出する**」仕様を述べましたが、ここでは**検出した後に人間が直す**方法を定義します。
320ページ撮り終えた後に「149ページと150ページの間に1枚抜けていた」と分かったとき、
**再撮影した1枚をどう挿入するか**が本節のテーマです。

#### 7.7.1 素朴な実装だと壊れる理由

最初に思いつくのは「間に挿入して、後ろを全部リネームする」ですが、これは危険です。

```
   挿入前: p0149  p0150  p0151  p0152 ... p0320
   挿入後: p0149  p0150  p0150.5(新) p0151 ... ???
              │
              └─ 後続を1つずつズラす必要がある
                 p0151→p0152, p0152→p0153, ... p0320→p0321
                 320-150 ≒ 170ファイルをリネーム

   問題点:
   ① 170ページ分の OCR 結果・レビュー状態(§11.7)・要確認フラグが
      すべて「別のページ番号」に付け替わる → 紐付けバグの温床
   ② 処理の途中(§8 の中間PNG等)でクラッシュすると、
      ファイルとJSONの対応がズレて全体が壊れる
   ③ レビューを終えた170ページを「未処理」に巻き戻すのは、
      §11.8の受け入れ基準(レビュー率5%以下)を台無しにする
```

#### 7.7.2 解決策: 「順番」と「実体」を分離する（安定ID + 並び順キー）

**REQ-PAGEMGMT-01**: 各ページに、ファイル名とは独立した**不変のページID**（UUID）を持たせ、
「本の中の並び順」は**別の数値（order_key）で管理する**。

```
  ❌ これまでの設計                    ✅ 挿入に強い設計

  ページ番号(p0150) が             ページID(UUID・不変)
   ＝ ファイル名                        │
   ＝ 並び順                            ├─ order_key: 150000.0  ← 並び順はコレだけが決める
   ＝ レビュー状態の紐付けキー           ├─ image_path: xxx.png
                                        └─ review_status: confirmed
  1個の値に4つの役目が集中
  → 挿入のたびに全部ズレる             ページ番号(表示用の "150" )は
                                       order_key を昇順ソートした「順位」を
                                       表示時に**都度計算**するだけ（保存しない）
```

**REQ-PAGEMGMT-02**: `order_key` は整数を隙間だらけ（既定 1000 刻み）で採番し、
挿入時は**前後の中間値**を割り当てる（フラクショナル・インデックス方式）。

```python
def insert_between(before_key: float, after_key: float) -> float:
    """2つの order_key の中間値を返す。他のページの order_key には一切触れない。"""
    return (before_key + after_key) / 2

# 例: p0149(order_key=149000) と p0150(order_key=150000) の間に挿入
new_key = insert_between(149000, 150000)   # → 149500.0
# p0150ページ以降のファイルは一切リネームしない。DB(JSON)に1行足すだけ。
```

```
   採番例（初期状態は1000刻み）:
   p0001=1000  p0002=2000  p0003=3000 ... p0150=150000  p0151=151000 ...
                                     │
                          ここに1枚挿入 → 149500 を新規追加
                                     ▼
   p0001=1000 ... p0149=149000  [新規=149500]  p0150=150000 ...
                                     ↑
                          表示上は「150ページ目」として自動で計算される
                          （149000 < 149500 < 150000 なので、ソート順で149と150の間に来る）
```

💡 **[学習メモ] フラクショナル・インデックス（Fractional Indexing）とは**
Notion や Figma のようなアプリで「アイテムをドラッグして並び替えても、
他のアイテムのデータが一切書き換わらない」のは、まさにこの技法のおかげです。

考え方はシンプルで、**順番を「整数の連番」ではなく「実数の大小関係」で表す**ことです。
連番だと挿入のたびに後続全部をズラす必要がありますが、実数なら**間の値を1つ計算するだけ**で済みます。

```
  数直線のイメージ:

  1000 ─────────── 2000 ─────────── 3000
   p1                p2                p3

  p1とp2の間に挿入したい → (1000+2000)/2 = 1500 を新しいキーにするだけ
  1000 ────── 1500 ────── 2000 ─────────── 3000
   p1          new         p2                p3
```

何度も同じ場所に挿入を繰り返すと理論上は数値の精度が問題になりますが（1500と2000の間にまた挿入→1750…）、
浮動小数点数は52bitの精度を持つため、**1冊の本で問題になることは現実的にありません**
（1箇所に1000回連続挿入しても精度は十分残ります）。心配な場合は定期的に「採番し直し（リナンバリング）」
のバッチを走らせれば解消します。

#### 7.7.3 UI操作と、裏側で起きること

**REQ-PAGEMGMT-03**: ページ一覧画面（§11.7.2）から、以下の操作を提供する。

## 8. 画像処理パイプライン（前処理）

### 8.1 なぜ前処理が必要か

OCRエンジンは「**まっすぐで・平らで・明暗が均一で・余計な物が写っていない**」画像を前提に作られています。
スマホ撮影の画像はその真逆なので、渡す前に整えます。

```
【撮ったまま】                    【前処理後】
┌────────────────┐              ┌──────────────┐
│ 机 机 机 机 机  │              │ ｜数式 が写真 │
│  ╱▔▔▔▔▔▔╲    │   ─────▶     │  本文テキスト │
│ │ 傾いた紙面 │   │              │  本文テキスト │
│ │ 影 影      │  │              │  本文テキスト │
│  ╲________╱   │              └──────────────┘
│ 机 机 指 机 机  │               白背景・水平・
└────────────────┘               余白トリム済み
  OCR精度 70%台                    OCR精度 99%台
```

### 8.2 工程一覧（実行順は固定）

| # | 工程 | 目的 | 主な手段 |
|---|---|---|---|
| P1 | **フォーマット変換** | HEIC/RAW(ARW等) → 可逆PNG（各ライブラリが扱える形に） | `pillow-heif`（HEIC）/ `rawpy`+`libraw`（RAW、§6.4.6） |
| P2 | **EXIF向き正規化** | 縦横が90度回っているのを直す | `PIL.ImageOps.exif_transpose` |
| P3 | **ページ矩形検出** | 机・指・背景を除去し、紙面だけ切り出す | 輪郭検出（`cv2.findContours`） |
| P4 | **台形補正** | 斜め撮影の歪みを長方形に戻す | 射影変換（`cv2.warpPerspective`） |
| P5 | **デスキュー** | 残った微小な傾き（±3度程度）を水平に | Hough変換 or 射影プロファイル |
| P6 | **見開き分割** | 見開き1枚 → 左右2ページに分ける | ノド（中央の暗い谷）検出 |
| P7 | **照明ムラ補正** | 影で暗い部分を明るく均一化 | 背景推定除算（モルフォロジー） |
| P8 | **ノイズ除去・シャープ化** | 粒状ノイズを消し、文字の輪郭を立てる | `fastNlMeansDenoising` + アンシャープ |
| P9 | **リサイズ正規化** | OCRが得意な解像度に揃える（約400dpi相当） | Lanczos 補間 |
| P10 | **保存** | 中間成果物としてPNGで保存（再実行可能に） | `cv2.imwrite` |

> **REQ-PRE-01**: 各工程の出力は `work/{book_id}/P{n}/` に保存し、任意の工程から再開できること（冪等性）。
> **REQ-PRE-02**: OCRエンジンに渡すのは **グレースケール** とする。二値化はエンジン側に任せる（後述）。

💡 **[学習メモ] 「二値化は自分でやらない」という判断**
古い OCR（Tesseract v3 など）は白黒2値の画像を要求しました。
しかし現代のディープラーニング系OCR（Apple Vision、yomitoku、Mathpix）は
**グレースケールの階調情報から特徴を学習**しているため、
自分で二値化すると「薄い添字」や「細いルビ」の情報を捨ててしまい、かえって精度が落ちます。
→ **仕様として「二値化しない」を明記**しておくのが重要です（良かれと思って追加されるのを防ぐ）。

### 8.3 P3-P4 台形補正の仕組み（図解）

```
       撮影画像（斜めから）              補正後
     A┌─────────────┐B            A'┌──────────┐B'
      ╲   数式 f(x)  ╲               │ 数式 f(x) │
       ╲             ╲     ────▶    │           │
       D╲___________╱C               │           │
                                    D'└──────────┘C'
   4隅 A,B,C,D を検出                 長方形 A',B',C',D' へ
                                      「引き伸ばす」
```

射影変換（ホモグラフィ）は、「4点をどこへ動かすか」を指定すると、
その間のすべてのピクセルを数学的に対応付けてくれる変換です。

```python
import cv2
import numpy as np

def correct_perspective(image: np.ndarray, corners: np.ndarray) -> np.ndarray:
    """4隅の座標を与えて、紙面を正面から見た長方形に変換する。

    corners : 形状 (4, 2) の配列。[左上, 右上, 右下, 左下] の順。
    """
    # 補正後のサイズを、元の辺の長さから推定する
    (tl, tr, br, bl) = corners
    width  = int(max(np.linalg.norm(tr - tl), np.linalg.norm(br - bl)))
    height = int(max(np.linalg.norm(bl - tl), np.linalg.norm(br - tr)))

    # 変換先の4隅（きれいな長方形）
    destination = np.array([
        [0, 0], [width - 1, 0], [width - 1, height - 1], [0, height - 1]
    ], dtype=np.float32)

    # 変換の「設計図」（3x3行列）を求めて、適用する
    matrix = cv2.getPerspectiveTransform(corners.astype(np.float32), destination)
    return cv2.warpPerspective(image, matrix, (width, height),
                               flags=cv2.INTER_LANCZOS4)   # 拡大時に文字が滑らかになる補間
```

💡 **[学習メモ] `np.ndarray` とは / 画像が「数字の表」である話**
OpenCV は画像を **NumPy の多次元配列** として扱います。
グレースケール画像なら `(高さ, 幅)` の2次元表で、各マスに 0〜255 の明るさが入っています。

```
        列0  列1  列2
 行0 [ 255  255  250 ]   ← 白い紙
 行1 [ 255   30   28 ]   ← 黒い文字の一部
 行2 [ 250   32  255 ]
```

`image.shape` で `(高さ, 幅)` が取れます。**行が先、列が後**です
（`(x, y)` ではなく `(y, x)` の順）。ここは初心者が必ず1回はハマる場所です。

`np.linalg.norm(tr - tl)` は「2点間の距離（ユークリッド距離）」。
`tr - tl` で座標の差ベクトルを作り、その長さを測っています。
中学で習う三平方の定理 `√((x₂-x₁)² + (y₂-y₁)²)` を1行で書いたものです。

#### 8.3.1 セッション単位の校正（1枚ごとの独立検出をやめる） ★追加要件

上記のP3-P4は「1枚ごとに独立して4隅を検出する」設計だが、これは§6.3のアーム固定式スタンドを使う前提では不必要にリスクを取っている。カメラは撮影セッション中ほぼ動かないため、**4隅検出はセッション開始時に1回だけ行い、以降は使い回す**方式に変更する。

```
  ❌ 1枚ごとに毎回ゼロから4隅を探す                ✅ セッション開始時に1回だけ校正

  写真1 → 4隅を検出 → 変換行列A                  写真1(校正用) → 4隅を検出・人間が確認
  写真2 → 4隅を検出 → 変換行列B(Aと微妙に違う)              ↓
  写真3 → 4隅を検出 → 失敗するかもしれない        変換行列を1つ確定・保存
  ...                                                    ↓
  300回、毎回「検出に失敗するリスク」を負う        写真2〜300 → 校正値を初期値(ヒント)として
                                                  近傍のみ再探索（誤検出の余地を大幅に縮小）
```

失敗しうる具体例: アクリル板自体がLED照明を反射して境界線として誤検出される、ページ端の色付きヘッダーを「ページの端」と誤認識する、見開きで隣のページが写り込み四角形と誤認識する、など。これらは「1枚ずつ独立検出」だと300回のどこかで偶発的に起こりうるが、「セッション開始時に1回だけ人間が確認」であれば、リスクは300回から1回に減る。

**REQ-PRE-03**: セッション開始時に校正を行い、以降のページは校正値をヒントとした狭い探索範囲でのみ4隅を再検出する。

```python
def calibrate_session(first_frame: np.ndarray) -> np.ndarray:
    """セッション最初の1枚から変換行列を求め、以降の全ページで使い回す。

    人間の確認ポイント: ここで検出した4隅を画面に表示し、
    OKならそのまま、ズレていれば手動でドラッグ修正してから確定する。
    """
    corners = detect_page_corners(first_frame)
    matrix = compute_perspective_matrix(corners)
    return matrix


def detect_with_hint(frame: np.ndarray, expected_corners: np.ndarray,
                     search_margin_px: int = 40) -> np.ndarray:
    """校正済みの4隅の"近く"だけを探す。ゼロから探すより誤検出が起きにくい。

    search_margin_px: 期待位置から何ピクセルの範囲内を探索するか
    """
    roi = expand_bbox(expected_corners, margin=search_margin_px)
    corners = detect_page_corners(frame, search_region=roi)
    if corners is None:
        return expected_corners   # 見つからなければ校正値をそのまま使う(フォールバック)
    return corners
```

💡 **[学習メモ] 「探索範囲を絞る」のがなぜ効くのか**
画像全体からいきなり「本らしき四角形」を探すと、アクリル板の反射・本の縁・隣のページなど**候補が複数**出て、間違ったものを選んでしまうリスクがあります。
「だいたいこの辺りにあるはず」という**事前知識(ヒント)**があると、探索範囲を数十ピクセル四方に絞れるので、**誤検出できる余地そのものが物理的になくなります**。総当たりで探す前にまず当たりをつける、という汎用的な高速化・安定化のテクニックです。

なお本の厚みで開いたときのノド位置がわずかにズレるため、変換行列をそのまま使い回すのではなく、この「ヒント付き狭域探索」で毎ページ微調整する設計にしている。

#### 8.3.2 補正結果の自動検査（アスペクト比サニティチェック）

300ページ全てを目視で確認するのは非現実的なため、§11のQA思想（見逃しを自動検出する）を前処理段階にも適用する。

**REQ-PRE-04**: 補正後の四角形が、想定するページの縦横比から大きく外れていないかを自動チェックし、外れていれば§11.7のレビュー画面に「前処理エラー」として流す。

```python
def check_aspect_ratio(corrected: np.ndarray, expected_ratio: float,
                       tolerance: float = 0.05) -> bool:
    """B5サイズなら 182/257 ≒ 0.708 のような期待比率と比べ、
    補正結果が想定外に歪んでいないかを検査する。
    """
    height, width = corrected.shape[:2]
    actual_ratio = width / height
    return abs(actual_ratio - expected_ratio) <= tolerance
```

この検査は台形補正(P3-P4)の失敗だけでなく、見開き分割(P6, §8.4)の失敗も間接的に検出できる（分割位置がずれると、片側のページの縦横比が想定から外れるため）。

### 8.4 P6 見開き分割の仕組み

見開きを撮った場合、中央の綴じ目（ノド）は**影で暗くなる**性質を利用します。

```
   画像を縦方向に足し合わせて「列ごとの暗さ」をグラフにする

   明るさ
    ▲
255 │▔▔▔▔▔▔▔▔▔▔╲    ╱▔▔▔▔▔▔▔▔▔▔
    │            ╲  ╱
    │             ╲╱   ← ここが最小＝ノド（綴じ目）
  0 └──────────────┼──────────────▶ x座標
    0             中央             幅
```

```python
def find_gutter_x(gray: np.ndarray) -> int:
    """見開き画像のノド（綴じ目）のx座標を返す。"""
    # 各列の平均明るさを計算する（axis=0 は「行方向に潰す」＝列ごとの平均）
    column_means = gray.mean(axis=0)

    # 中央±15%の範囲だけを探索対象にする（端の暗さに引っ張られないように）
    width = gray.shape[1]
    lo, hi = int(width * 0.35), int(width * 0.65)

    # その範囲で最も暗い列を探す
    return lo + int(np.argmin(column_means[lo:hi]))
```

💡 **[学習メモ] `axis` の意味**
`gray.mean(axis=0)` の `axis=0` は「0番目の軸（＝行方向）に沿って潰す」という意味。
`(高さ3000, 幅4000)` の画像なら、結果は長さ 4000 の1次元配列（＝各列の平均）になります。
逆に `axis=1` なら各行の平均（長さ3000）。
**「潰す軸を指定する」** と覚えると混乱しません。

### 8.5 P7 照明ムラ補正の仕組み

```
  【補正前】                    【補正後】
  明るさ                        明るさ
   ▲  ╱▔▔▔╲                    ▲ ▔▔▔▔▔▔▔▔
   │ ╱      ╲___              │
   │╱  文字↓     ╲             │   文字↓
   │   |  |       ╲            │   |  |  |  |
   └──────────────▶            └──────────────▶
  背景自体が波打っている        背景がフラット＝閾値が1つで済む
```

やり方は「**背景だけの画像を推定して、それで割り算する**」です。

```python
def flatten_illumination(gray: np.ndarray) -> np.ndarray:
    """照明ムラを除去して、紙の白さを均一にする。"""
    # 1) 大きなカーネルで「閉じる」と、暗い文字が白で塗り潰され、背景（照明ムラ）だけが残る
    kernel = cv2.getStructuringElement(cv2.MORPH_ELLIPSE, (51, 51))
    background = cv2.morphologyEx(gray, cv2.MORPH_CLOSE, kernel)

    # 2) 元画像 ÷ 背景 → 背景が1.0になり、文字だけが暗く残る
    normalized = cv2.divide(gray, background, scale=255)
    return normalized
```

💡 **[学習メモ] モルフォロジー演算の直感**
`MORPH_CLOSE`（クロージング）は「暗い細いもの（＝文字）を白で塗り潰す」操作です。
51×51 という大きなカーネル（＝筆）で塗るので、文字はすべて消え、
**ゆっくり変化する照明ムラだけが残った「背景画像」** が得られます。
あとは `元画像 ÷ 背景画像` とすれば、ムラの影響が打ち消されます。
「シミのついた紙に書かれた字を読むとき、シミの濃さを差し引いて読む」のと同じ発想です。

## 9. OCR エンジン仕様

### 9.1 「1つのエンジンで全部やる」は失敗する

これが本システムの最重要の設計判断です。

```
   ❌ 単一エンジン                    ✅ ハイブリッド（本仕様）

  ┌─────────────┐                  ┌──────────────┐
  │  ページ画像  │                  │  ページ画像   │
  └──────┬──────┘                  └───────┬──────┘
         ▼                                 ▼
  ┌─────────────┐                  ┌──────────────┐
  │ 汎用OCR      │                  │ レイアウト解析 │
  │             │                  │ (領域を分類)   │
  └──────┬──────┘                  └───┬───┬───┬──┘
         ▼                     本文 ───┘   │   └─── 図
  "F = qv x B"                          数式│
  "12 のt"  ← 分数が壊れた         ┌────────┘
  縦書きで行が混線                  ▼
                          ┌────────────────┐
                          │ 数式特化OCR      │
                          │ → \frac{1}{2}   │
                          └────────────────┘
```

数式は「2次元の配置そのものに意味がある」（上付き・下付き・分数・∑の上下）ので、
「左から右に文字を並べる」前提の汎用OCRでは原理的に扱えません。

### 9.4 検討: DeepSeek-OCR / DeepSeek-OCR-2 の採否

2025年10月に公開された **DeepSeek-OCR** は、「文書画像を少数の視覚トークンに圧縮し、そこからテキストを復元する」という新しい設計（Contexts Optical Compression）を採用したOSSモデルです。2026年1月には後継の **DeepSeek-OCR-2**（OmniDocBench v1.5で91.09%）が公開されています。

```
【従来のOCR】                      【DeepSeek-OCR の発想】
文書画像                           文書画像
  │ 1文字ずつ認識                     │ 少数の「視覚トークン」に圧縮
  ▼                                  ▼
テキスト                           視覚トークン（画像の「圧縮ファイル」）
                                     │ デコード（展開）
                                     ▼
                                   テキスト（ほぼ元通り復元）
```

| 項目 | 内容 |
|---|---|
| アーキテクチャ | DeepEncoder（SAM-base 80M + CLIP）+ DeepSeek3B-MoE-A570M（実働570M） |
| 圧縮性能 | Fox ベンチマークで、視覚トークンをテキストトークンの1/10に圧縮しても精度96〜98%維持。1/20圧縮でも約60% |
| OCR-2 の新機軸 | 「Causal Visual Flow」＝ 左上→右下の機械的走査順ではなく、意味を見ながら動的に読み順を並べ替える方式（§10.3 の読み順問題と直結する研究テーマ） |
| Mac対応 | MPS backend 対応済み。`mlx-community/DeepSeek-OCR-8bit` で MLX 実行可。必要メモリは16GB以上（32GB推奨）と**極めて軽量** |

**採用しない理由（縦書き）**: 学術評価（Evaluating Multimodal LLMs on Vertically Written Japanese Text, arXiv:2511.15059）で、DeepSeek-OCR は横書き日本語では良好な一方、**縦書き日本語で大きく精度が劣化**し、同条件の PaddleOCR-VL より劣化幅が大きいことが確認されている。国語（§4 US-05、縦書き＋ルビ）が本仕様の必須要件であるため、**縦書きへの適用は不採用**とする。

**採用する理由（横書き・第3エンジン）**: 実働570Mという軽さは、Apple Vision・yomitokuに次ぐ「3人目の目」を追加するコストをほぼゼロにする。2エンジンの食い違いは「不一致」までしか判定できないが、3エンジンなら§11.2の多数決で自動的に決着できるケースが増える。

**数式への適用は保留**: 数式（特に添字・分数構造）に対する定量的な精度評価は確認できておらず、**§18のテスト計画（評価データセットでのCER測定）を経てから本採用を判断する**。仕様として断定しない。

### 9.5 検討: ローカルVLM（大容量メモリMac向け）

192GBのような大容量統合メモリMacでは、Mathpix API を補完・代替する第3の数式エンジンとして、量子化したローカルVLM（Qwen2.5-VL 72Bなど）を常駐させる選択肢がある。

| モデル | 必要メモリ(4bit量子化) | 用途 |
|---|---|---|
| Qwen2.5-VL 72B (4bit) | 約40GB | 数式OCRの第3エンジン候補 |
| DeepSeek-OCR-2 (8bit, MLX) | 数GB | 横書き本文の第3エンジン（§9.4） |

両方を同時に常駐させても192GB環境では合計50GB程度に収まり、**十分な余裕がある**。ただし、これらはオフラインで課金なく動く利点と引き換えに、Mathpixほど数式特化で学習されていないため、§18のテストで精度を実測してから本番投入の可否を決める（`config/default.yaml` の `engines.math.local_vlm.enabled` フラグで有効/無効を切り替え可能にする）。

**REQ-OCR-05**: `iogpu.wired_limit_mb` 等のシステム全体設定の変更は、システム安定性への影響が大きいため、まず量子化（4bit）で運用し、精度不足が実測で確認された場合のみ検討する。

### 9.6 抽象化インターフェース（差し替え可能にする）

エンジンは今後も入れ替わるので、**共通の型で包んで**おきます。

```python
from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)

class OcrEngine(Protocol):

    name: str
    def recognize(self, image: np.ndarray, vertical: bool = False) -> list[OcrLine]:
        ...
```

💡 **[学習メモ] `@dataclass` とは**
「データを入れるだけのクラス」を1行で作れる機能です。
これがないと、`__init__` や `__repr__` を手で書く必要があります。

```python
# dataclass を使わない場合（長い）
class OcrLine:
    def __init__(self, text, bbox, confidence, engine, kind):
        self.text = text
        self.bbox = bbox
        # ... 以下延々と

# dataclass を使う場合（上のコード）→ 型を書くだけで同じものができる
```

`frozen=True` を付けると **作った後に値を変更できなくなります**（イミュータブル）。
OCR結果は「事実の記録」なので、途中で書き換わると原因追跡が困難になります。
**壊れないように鍵をかけておく**のが目的です。

💡 **[学習メモ] `Protocol` とは（ダックタイピングの明文化）**
「`name` という属性と `recognize` というメソッドさえ持っていれば、
中身が何であれ OCR エンジンとして扱ってよい」という**型の約束**を書いたものです。

```
  「アヒルのように歩き、アヒルのように鳴くなら、それはアヒルだ」

  AppleVisionEngine ─┐
  YomitokuEngine   ─┼─▶ どれも recognize() を持つ ─▶ 同じように使える
  MathpixEngine    ─┘
```

継承（`class YomitokuEngine(OcrEngine):`）を書かなくても成立するのが `Protocol` の利点で、
外部ライブラリのクラスもそのまま当てはめられます。これにより、
**エンジンを差し替えても呼び出し側のコードを一切変えずに済みます。**

### 10.3 読み順の決定

```
【横書き 2段組】                    【縦書き（国語）】
┌──────────┬──────────┐            ┌───────────────────┐
│ ①        │ ③        │            │ ③   ②   ①        │
│ 本文     │ 本文     │            │ 本  本  本        │
│ ②        │ ④        │            │ 文  文  文        │
│ 数式     │ 図       │            │ ↓   ↓   ↓        │
└──────────┴──────────┘            └───────────────────┘
 左列を上→下、次に右列を上→下        右列から左へ、各列は上→下
```

**REQ-LAYOUT-03**: 縦書き判定は以下で行い、ページ単位で確定させる（行ごとに切り替えない）。

```python
def is_vertical_layout(lines: list[OcrLine]) -> bool:
    """行領域の形状から、縦書きページかどうかを判定する。

    考え方: 横書きの行は「横長」、縦書きの行は「縦長」の長方形になる。
    """
    if not lines:
        return False

    vertical_count = 0
    for line in lines:
        _, _, w, h = line.bbox
        if h > w * 1.5:          # 縦長 = 縦書きの行
            vertical_count += 1

    # 行の6割以上が縦長なら、このページは縦書きとみなす
    return vertical_count / len(lines) >= 0.6
```

**REQ-LAYOUT-04**: 読み順ソートは以下とする。

| レイアウト | ソートキー |
|---|---|
| 横書き1段 | `(y, x)` の昇順（上から下、同じ高さなら左から右） |
| 横書き2段 | 列を検出して分割 → 列ごとに `(y, x)` 昇順 → 左列 → 右列 |
| 縦書き | `(-x, y)` の昇順（**右から左**、各列は上から下） |

💡 **[学習メモ] `-x` で降順にするテクニック**
Python の `sorted()` は昇順が基本です。「x が大きい順（右から左）」にしたいときは、
符号を反転させた `-x` をキーにすると昇順ソートのまま降順が実現できます。

```python
lines.sort(key=lambda ln: (-ln.bbox[0], ln.bbox[1]))
#                           ^^^^^^^^^^  x を反転 = 右から左
#                                       ^^^^^^^^ 同じ列内は y 昇順 = 上から下
```

タプルをキーにすると「第1キーで比べ、同点なら第2キーで比べる」という
**多段ソート**になります。エクセルの「並べ替え → 第2条件を追加」と同じです。

## 11. 誤読を防ぐ品質保証設計 ★最重要

「読み込みミスを防ぐ」という要求に対する、本仕様の中心部です。
**「ミスをゼロにする」ことは不可能**なので、方針を次のように定めます。

> **方針: ミスを『起こさない』のではなく、『必ず検出して人間に見せる』。
> そして、人間が見る量を全体の5%以下に絞る。**

```
       誤読 100件発生                 誤読 100件発生
            │                              │
   ┌────────┴────────┐          ┌──────────┴──────────┐
   │  何もしない      │          │  5層の検出ネット      │
   └────────┬────────┘          └──────────┬──────────┘
            ▼                               ▼
    100件が静かに混入          95件を自動検出 → レビューへ
    （どこが間違いか不明）       5件が漏れる（既知のリスクとして記録）
       😱 信用できない教材        ✅ 実用的な品質
```

### 11.1 そもそも何を間違えるのか（誤読パターン台帳）

対策は「敵を知る」ことから始まります。

#### A. 日本語で混同されやすい字

| 正 | 誤られやすい相手 | 対策 |
|---|---|---|
| `ロ`(カタカナ) | `口`(くち) `□`(記号) `0` | 文脈辞書（§11.6）／前後がカタカナかで判定 |
| `一`(いち) | `ー`(長音) `‐`(ハイフン) `−`(マイナス) `─`(罫線) | 前後の文字種で判定。数式内なら `−` を優先 |
| `カ` | `力`(ちから) | 物理教科書では「力」が頻出 → 分野辞書で重み付け |
| `ヘ` | `へ`(ひらがな) | 文字高の比較（カタカナは全角高） |
| `ニ` | `二`(漢数字) | 数式文脈なら `2`、助詞文脈なら `に` |
| `工` | `エ`(カタカナ) `土` | 辞書 |
| `巳/已/己` | 相互 | 低頻度 → 常に要確認フラグ |
| 旧字体 `學/國/藝` | 新字体と混同 | 国語（古文）で頻出。旧字辞書を別途持つ |

#### B. 数式で混同されやすい記号 ★事故が起きやすい

| 正 | 誤られやすい相手 | なぜ危険か |
|---|---|---|
| `x`（変数） | `×`（かける） `X` | **意味が完全に変わる**。`a x b` と `a × b` |
| `-`（マイナス） | `−` `–` `—` `ー` | LaTeXコンパイルは通るが、コピーして計算に使えない |
| `l`（エル） | `1`（いち） `\|`（縦棒） `I` | `l` と `1` は書体によりほぼ同形 |
| `0`（ゼロ） | `O`（オー） `o` `θ` | `θ` との混同は物理で致命的 |
| `α` | `a` | ギリシャ文字全般が危険（`ν` と `v`、`ρ` と `p`、`κ` と `k`） |
| 上付き `x^2` | 並び `x2` | **添字構造の消失**。これが最頻出の事故 |
| 下付き `a_1` | 並び `a1` | 同上 |
| `\frac{a}{b}` | `a / b` や `a b` | 分数線の見落とし |
| `\int` | `f` `S` | 積分記号を筆記体Sと誤認 |
| `\sum_{i=1}^{n}` | `Σ` のみ（上下限落ち） | 上下限の欠落は沈黙のバグ |

> 認識結果にこれらが含まれる場合は信頼度を減点して検出ネットに掛ける。

### 11.2 【第1層】アンサンブル照合（多数決）

**REQ-QA-02**: 本文は2エンジン、数式は2エンジンで独立に認識し、結果を突き合わせる。

```
                    ┌──── Apple Vision ───▶ "運動方程式は ma = F"
   同じ画像 ────────┤
                    └──── yomitoku ───────▶ "運動方程式は ma = F"
                                                    │
                                        ┌───────────┴───────────┐
                                        │  文字ごとにアライメント  │
                                        └───────────┬───────────┘
                                                    ▼
                                     完全一致 → 信頼度 UP（0.99）採用
                                     不一致   → ⚠️ 要確認フラグ
```

```python
from difflib import SequenceMatcher

def cross_check(text_a: str, text_b: str) -> tuple[str, float, list[str]]:
    """2エンジンの結果を突き合わせ、(採用テキスト, 信頼度, 不一致箇所) を返す。"""
    matcher = SequenceMatcher(None, text_a, text_b)
    similarity = matcher.ratio()          # 0.0〜1.0 の類似度

    disagreements = []
    for tag, i1, i2, j1, j2 in matcher.get_opcodes():
        if tag != "equal":
            disagreements.append(f"[{tag}] A='{text_a[i1:i2]}' / B='{text_b[j1:j2]}'")

    # 一致していれば A を採用（どちらでも同じ）。不一致なら主エンジンを採用しフラグを立てる
    return text_a, similarity, disagreements
```

💡 **[学習メモ] `difflib.SequenceMatcher` とは**
Python 標準ライブラリに入っている「2つの文字列の違いを見つける道具」です。
Git の差分表示と同じ仕組み（最長共通部分列）で動きます。

```
  A: "ma = F"
  B: "rna = F"
        ↑
  get_opcodes() が返すもの:
    ('replace', 0, 1, 0, 2)  → A の 0〜1文字目 "m" が B では "rn" になっている
    ('equal',   1, 6, 2, 7)  → 残りは一致
```

`m` を `rn` と読み違えるのは OCR の古典的失敗です。
**外部ライブラリ不要で実装できる**ので、最初に入れるべき検査です。

**REQ-QA-03**: 判定閾値

| 類似度 | 扱い |
|---|---|
| `= 1.00` | 自動採用（信頼度 0.99） |
| `0.95 〜 0.99` | 自動採用だが差分箇所をハイライト（信頼度 0.85） |
| `< 0.95` | **要確認**としてレビューキューへ |

#### 11.2.1 拡張: 3エンジン多数決（REQ-ARCH-02 該当環境）

大容量メモリMac（§5.3, §9.5）では第3エンジンが追加されるため、2者照合の弱点を解消できる。

```
   【2エンジン】不一致＝「要確認」で終わり              【3エンジン】不一致でも多数決で決着できる

   Apple Vision ──▶ "F = ma"                       Apple Vision  ──▶ "F = ma"
                              不一致                DeepSeek-OCR  ──▶ "F = ma"     ──▶ 2対1で "F = ma" を自動採用
   yomitoku     ──▶ "F = rna"  ⚠️要確認              yomitoku      ──▶ "F = rna"        （要確認には回さない）
```

**REQ-QA-03b**: 3エンジン構成では以下の優先順で決定する。

```
  3つの認識結果 A, B, C を突き合わせる
        │
        ├─ 3つとも完全一致        → 自動採用（信頼度 0.995）
        ├─ 2つが完全一致（多数決）  → 多数側を自動採用（信頼度 0.95）
        └─ 3つとも不一致          → 要確認（もっとも疑わしい＝レビューへ）
```

```python
from collections import Counter

def majority_vote(text_a: str, text_b: str, text_c: str) -> tuple[str, float, bool]:
    """3エンジンの結果を多数決する。(採用テキスト, 信頼度, 要確認フラグ) を返す。"""
    counts = Counter([text_a, text_b, text_c])
    winner, votes = counts.most_common(1)[0]   # 最も多く出現したテキストと、その票数

    if votes == 3:
        return winner, 0.995, False       # 満場一致
    if votes == 2:
        return winner, 0.95, False        # 2対1の多数決
    return text_a, 0.40, True             # 3者バラバラ → 主エンジン(A)を仮採用してレビューへ
```

💡 **[学習メモ] `Counter.most_common(1)`**
`Counter` は「リストの中で、各要素が何回出現したか」を数えてくれる辞書のような型です。
`most_common(1)` は「最も出現回数が多いものを1つ、`(値, 回数)` のタプルで返す」という意味。

```
  Counter(["F=ma", "F=ma", "F=rna"])
       ↓
  {"F=ma": 2, "F=rna": 1}
       ↓ most_common(1)
  [("F=ma", 2)]   ← リストの中の最初のタプルを取り出すので [0] を付ける
```

**REQ-QA-03c**: 数式（LaTeX）は文字列の完全一致ではなく、空白や `{1}` ⇔ `{ 1 }` のような無意味な表記ゆれを除去する正規化処理を経てから比較する。`\frac{1}{2}` と `\frac{1} {2}` のような差異だけで多数決が割れないようにするため（正規化ルール自体は §11.4 の構文チェックと合わせて実装する）。

### 11.3 【第2層】信頼度スコアによる振り分け

**REQ-QA-04**: 各行の最終信頼度を、以下の重み付き幾何平均で算出する。

```
                                  w1     w2     w3     w4
  final_confidence = (engine_conf  × agree  × penalty × context)
                                                                 ^(1/Σw)

  engine_conf : エンジン自身が返す自信度     w1 = 3
  agree       : アンサンブル一致度           w2 = 4  ← 最重視
  penalty     : 混同ペア出現による減点       w3 = 2
  context     : 辞書・文法整合性             w4 = 1
```

```python
def combine_confidence(engine_conf: float, agree: float,
                       penalty: float, context: float) -> float:
    """4つの指標を重み付き幾何平均で1つのスコアにまとめる。"""
    weights = {"engine": 3, "agree": 4, "penalty": 2, "context": 1}
    values  = {"engine": engine_conf, "agree": agree,
               "penalty": penalty, "context": context}

    total_weight = sum(weights.values())
    product = 1.0
    for key, weight in weights.items():
        product *= max(values[key], 1e-6) ** weight   # 0除算・0乗を避ける

    return product ** (1 / total_weight)
```

💡 **[学習メモ] なぜ「算術平均」ではなく「幾何平均」なのか**
算術平均（足して割る）だと、**1つが致命的に低くても他で埋め合わせできてしまいます**。

```
  算術平均: (0.99 + 0.99 + 0.99 + 0.05) / 4 = 0.755  ← 高く見える😱
  幾何平均: (0.99 × 0.99 × 0.99 × 0.05)^(1/4) = 0.47  ← ちゃんと低い✅
```

品質検査では「**どれか1つでもダメなら全体がダメ**」としたいので、
掛け算ベースの幾何平均が適切です。
「チェーンの強さは最も弱い輪で決まる」という考え方をそのまま式にしたものです。

**REQ-QA-05**: 信頼度による振り分け

| final_confidence | 扱い |
|---|---|
| `≧ 0.95` | 自動採用（レビュー不要） |
| `0.80 〜 0.95` | 自動採用 + 出力に `⚠️` マーカー付与 |
| `< 0.80` | **レビューキューへ**（人間が確認） |

### 11.4 【第3層】LaTeX 構文検証

数式は「コンパイルが通るか」で機械的に検証できます。これは強力です。

**REQ-QA-06**: すべての LaTeX 出力に対し、構文チェックを行う。

```
   Mathpix出力: "\frac{1}{2}mv^2"
         │
         ├─▶ ① 括弧の対応チェック（{ } [ ] の数と入れ子）
         ├─▶ ② コマンド存在チェック（\fracc のようなtypo検出）
         ├─▶ ③ 引数個数チェック（\frac は必ず引数2個）
         └─▶ ④ 実コンパイル（KaTeX / latexmk でエラーが出ないか）
                    │
              エラー → 要確認キューへ
```

```python
def check_brace_balance(latex: str) -> bool:
    """LaTeX の括弧の対応が取れているかを、スタックで検査する。"""
    pairs = {"}": "{", "]": "[", ")": "("}
    stack: list[str] = []

    index = 0
    while index < len(latex):
        char = latex[index]
        if char == "\\":          # \{ や \} はエスケープなので括弧として数えない
            index += 2
            continue
        if char in "{[(":
            stack.append(char)
        elif char in pairs:
            if not stack or stack.pop() != pairs[char]:
                return False       # 閉じ括弧が余っている or 種類が違う
        index += 1

    return len(stack) == 0        # 開き括弧が残っていたら失敗
```

💡 **[学習メモ] スタック（LIFO）の使いどころ**
「最後に開いたものを最初に閉じる」という構造を検査するときの定番アルゴリズムです。

```
  入力: \frac{ a { b } }
  ┌─────────────────────────────┐
  │ '{' を見たら  → 積む         │   スタック: [ {, { ]
  │ '}' を見たら  → 取り出す     │           → [ { ]
  │ 最後に空なら  → 対応OK ✅    │           → [ ]  ✅
  └─────────────────────────────┘
```

たとえるなら**皿の積み重ね**。上から順にしか取れません。
`list` の `append()`（積む）と `pop()`（取り出す）だけで実装できます。

### 11.5 【第4層】数式の意味的サニティチェック

構文が通っても、意味が壊れていることがあります。そこで **SymPy** で数式を解釈させます。

**REQ-QA-07**: LaTeX を SymPy でパースし、以下を検査する。

| 検査 | 検出できる誤読の例 |
|---|---|
| パース可能か | `x^` のような不完全な式 |
| 自由変数の一覧 | 突然 `l`（エル）が出現 → `1` の誤読を疑う |
| 次元・単位の整合（物理） | `F = ma` の両辺の次元が合わない |
| 数値代入による検算 | `(a+b)^2 = a^2 + 2ab + b^2` のような恒等式が崩れていないか |

```python
from sympy.parsing.latex import parse_latex
from sympy import symbols

SUSPICIOUS_SYMBOLS = {"l", "O", "I"}   # 1, 0, 1 と誤読されやすい

def semantic_check(latex: str) -> tuple[bool, list[str]]:
    """LaTeX を数式として解釈できるか、怪しい記号がないかを調べる。"""
    warnings = []
    try:
        expression = parse_latex(latex)
    except Exception as error:          # パース失敗＝構造が壊れている可能性大
        return False, [f"数式として解釈できません: {error}"]

    # 式に出てくる変数名を集める
    used = {str(s) for s in expression.free_symbols}
    for name in used & SUSPICIOUS_SYMBOLS:
        warnings.append(f"変数 '{name}' は数字の誤読かもしれません（l↔1, O↔0）")

    return True, warnings
```

💡 **[学習メモ] `set` の `&`（積集合）**
`used & SUSPICIOUS_SYMBOLS` は「両方に共通して含まれる要素」を取り出す演算です。

```
  used              = {"x", "l", "v"}
  SUSPICIOUS_SYMBOLS = {"l", "O", "I"}
                    &
                   ─────
  結果               = {"l"}     ← 共通するのは l だけ
```

`for name in used: if name in SUSPICIOUS_SYMBOLS:` と書くのと同じですが、
集合演算のほうが**意図が一目でわかり、しかも高速**です（集合は内部でハッシュ表を使う）。

💡 **[学習メモ] `except Exception as error` の意味**
`parse_latex()` は壊れた数式を渡されると例外（エラー）を投げてプログラムを止めます。
`try / except` で囲むと「エラーが起きても止まらず、その場合の処理に進む」ようにできます。
**300ページの処理が1つの数式で止まってはいけない**ので、
パイプラインの各工程は必ず例外を捕まえ、「失敗した」という記録を残して次へ進む設計にします。

### 11.6 【第5層】文脈辞書による補正

**REQ-QA-08**: 教科書ごとに専用の語彙辞書を自動生成し、認識結果を補正する。

```
  ① 索引ページ・目次ページを先にOCR
        ↓
  ② 「運動量」「ベクトル」「導関数」… を抽出 → 専門用語リスト
        ↓
  ③ 分野別の共通辞書とマージ
     physics.txt : 加速度, 慣性, 電磁誘導, ローレンツ力, ...
     math.txt    : 微分, 積分, 収束, 写像, 単射, ...
     kokugo.txt  : 旧字体・古語・人名 ...
        ↓
  ④ 本文OCR結果の各単語を辞書と照合
        ↓
     辞書に無い かつ 辞書内の語と編集距離1 → 「誤読の可能性」として提示
```

💡 **[学習メモ] 編集距離（レーベンシュタイン距離）**
「1文字の挿入・削除・置換を何回すれば、片方の文字列をもう片方にできるか」という指標です。

```

  "微分"        → "積分"            ： 微 を 積 に置換（1回） → 距離 1
```

距離1は「タイプミス／OCR誤読の典型」なので、自動修正の候補にできます。
ただし上の `微分 → 積分` のように**距離1でも全く別の意味**になることがあるため、

> **REQ-QA-09**: 辞書による自動修正は行わず、**候補提示のみ**とする。
> 採否は人間が決める（レビューUI上でワンキー適用）。

とします。「賢い自動修正」は、静かに間違いを増やす最大の原因です。

### 11.8 受け入れ基準（品質ゲート）

**REQ-QA-10**: リリース判定は、以下の**評価用データセット**に対する測定値で行う。

| 項目 | 内容 |
|---|---|
| 評価データ | 物理30ページ / 数学30ページ / 国語（縦書き）20ページ を人手で正解作成 |
| 測定指標1 | **CER**（文字誤り率, Character Error Rate）= 編集距離 ÷ 正解文字数 |
| 測定指標2 | **数式行正解率** = 完全一致した数式行 ÷ 全数式行 |
| 測定指標3 | **検出率（Recall）** = 検出された誤読 ÷ 実際の誤読 ← **最重要** |
| 測定指標4 | **レビュー率** = 要確認行 ÷ 全行 |

| 指標 | 合格ライン |
|---|---|
| 本文 CER | ≦ 0.5%（＝ 99.5% 以上） |
| 数式行正解率 | ≧ 95% |
| 誤読の検出率 | **≧ 95%**（見逃しが5%以下） |
| レビュー率 | ≦ 5%（人間の負担の上限） |

💡 **[学習メモ] なぜ「検出率」が精度より大事なのか**
精度98%のシステムAと、精度95%だが誤りの99%を検出できるシステムBを比べます。

```
  A: 1000行中20行が誤り。どれが誤りか分からない → 全1000行を目視 = 使えない
  B: 1000行中50行が誤り。うち49行に印が付く   → 印の付いた行だけ直す = 実用的
```

**「間違えないこと」より「間違いを自覚できること」のほうが価値がある** ―
これは自動化システム全般に言える設計原則です。

💡 **[学習メモ] なぜ「各エンジンの生の結果」を全部残すのか**
`engines` に両方の結果を保存しておくのは冗長に見えますが、これは意図的です。

1. **後から検証できる**: 「なぜこの行が要確認になったのか」を追跡できる
2. **エンジンを再評価できる**: 「yomitoku の方が実は良かった」と分かったとき、再撮影せずに採用を切り替えられる
3. **統計が取れる**: どのエンジンがどの分野で強いかを測定し、次の設計に活かせる

データは**捨てるのは一瞬、取り直すのは数時間**です。中間データは全部残す方針にします。

### 12.2 Python 側の型定義

```python
from dataclasses import dataclass, field
from enum import Enum

class BlockKind(str, Enum):
    """領域の種別。文字列としても扱えるEnum。"""
    BODY_TEXT  = "body_text"
    MATH_BLOCK = "math_block"
    MATH_INLINE = "math_inline"
    FIGURE     = "figure"
    CAPTION    = "caption"
    TABLE      = "table"
    HEADER     = "header"
    FOOTER     = "footer"

@dataclass
class Issue:
    code: str          # "ENGINE_DISAGREE" など機械可読なコード
    detail: str        # 人間向けの説明
    severity: str      # "low" | "medium" | "high"

@dataclass
class Block:
    block_id: str
    kind: BlockKind
    bbox: tuple[int, int, int, int]
    reading_order: int
    text: str = ""
    latex: str = ""
    confidence: float = 0.0
    issues: list[Issue] = field(default_factory=list)
    review_status: str = "pending"      # pending | confirmed | edited | skipped（§11.7.4）
    edited_by: str | None = None        # None=自動採用 / "user"=手動修正（REQ-UI-09）
    edited_at: str | None = None        # ISO8601。修正が行われた時刻

    @property
    def needs_review(self) -> bool:
        """レビューが必要かを判定する（§11.5 の閾値）。"""
        return self.confidence < 0.80 or any(i.severity == "high" for i in self.issues)


@dataclass
class Page:
    page_id: str                        # UUID。挿入・削除・並べ替えでも不変（§7.7.2）
    order_key: float                    # 並び順キー。挿入時は前後の中間値を割り当てる（REQ-PAGEMGMT-02）
    image_path: str
    layout: str = "horizontal"          # horizontal | vertical（§10.3）
    printed_number: int | None = None
    deleted: bool = False               # 論理削除フラグ（§7.7.3）
    warnings: list[str] = field(default_factory=list)
    blocks: list[Block] = field(default_factory=list)

    @property
    def needs_review(self) -> bool:
        """このページ内に要確認ブロックが1つでもあるか。"""
        return any(b.needs_review for b in self.blocks)


def compute_display_page_index(pages: list[Page]) -> dict[str, int]:
    """order_key を昇順ソートし、削除されていないページに表示用の連番を振る。

    重要: この結果はJSONに保存しない（REQ-PAGEMGMT-05）。表示のたびに計算する。
    """
    visible = sorted((p for p in pages if not p.deleted), key=lambda p: p.order_key)
    return {p.page_id: index for index, p in enumerate(visible, start=1)}
```

💡 **[学習メモ] `field(default_factory=list)` を使う理由**
リストを初期値にしたいとき、`issues: list[Issue] = []` と書くと**重大なバグ**になります。
このリストは「クラス定義が読み込まれたとき1回だけ」作られ、
**全インスタンスで同じリストが共有されてしまう**からです。

```
   ❌ = []                     ✅ = field(default_factory=list)

   Block A ─┐                  Block A ──▶ [ ]
            ├──▶ [ 同じ箱 ]
   Block B ─┘                  Block B ──▶ [ ]
   A に追加すると B にも入る      それぞれ独立した箱
```

`default_factory=list` は「インスタンスを作るたびに `list()` を呼んで新しい空リストを作れ」
という指示です。Python 初心者が最もハマる落とし穴のひとつなので、
**「dataclass の初期値に list / dict を直書きしない」** と覚えてください。

💡 **[学習メモ] `@property` とは**
メソッドなのに、`()` なしで**属性のように呼べる**ようにする仕組みです。

```python
block.needs_review        # ✅ @property あり → True / False が返る
block.needs_review()      # @property なしならこう書く必要がある
```

「計算して求まるが、概念的には『そのオブジェクトの性質』であるもの」に使います。
`needs_review` は保存されたデータではなく毎回計算されるので、
`confidence` を書き換えれば自動的に結果も変わります（＝矛盾が起きない）。

| 保存先の種類 | 可否 | 注意点 |
|---|---|---|

**REQ-STORE-05**: 保存先が外部ボリューム（外付けドライブ等）で、処理中に切断（アンマウント）された場合、その時点までの中間成果物は保持したまま安全に処理を中断し、次回同じボリュームが接続された時点から `--from` で再開できるようにする（§8.2 REQ-PRE-01 の冪等性を活用）。

> 💡 **[学習メモ] なぜ「設定の優先順位」を明文化するのか**
> 「コマンドライン引数」「設定画面での保存」「設定ファイルの既定値」「アプリ自体の初期値」のように、
> 同じ項目を決める場所が複数あると、**どれが実際に使われるか分からなくなる**というバグの温床になります。
> このような場合は「①が指定されていれば①、なければ②、…」という**優先順位の連鎖**を最初に決めておくと、
> 後から「なぜこのフォルダに保存されたのか」を必ず1本の道筋で説明できます。
> Python での典型的な書き方は `output_dir = cli_arg or per_book_setting or config_default or FALLBACK` のように、
> `or` 演算子を使って「最初に真値（Noneでも空文字でもない値）になったものを採用する」という書き方です。

```
        │

        └─ Mathpix はレート制限があるため、数式OCRのみ同時2まで
```

**REQ-PERF-01**: 300ページの一括処理を60分以内に完了すること。
**REQ-PERF-02**: 処理はページ単位で並列化し、ワーカー数は設定で変更可能とする（既定 = CPUコア数 ÷ 2）。
**REQ-PERF-03**: 進捗を `rich` の進捗バーで表示し、中断（Ctrl+C）後も `--from` で再開できること。

💡 **[学習メモ] なぜ「ワーカー数 = コア数 ÷ 2」なのか**
画像処理は CPU をフルに使う（CPUバウンド）ため、コア数だけ並列化したくなります。
しかし実際には、

- OpenCV 自体が内部でマルチスレッド化している（重複して食い合う）
- 48MP 画像1枚は中間バッファ込みで実効ピーク約880MB使う（§5.3参照。8並列だと7GB超）
- Mac の電力管理で高効率コアは遅い

ため、**控えめから始めて実測で調整する**のが正解です。
「並列数を増やせば速くなる」は、ある点を超えると逆転します（**スラッシング**）。

### 15.2 大容量メモリMac（192GB級）での並列数

**REQ-ARCH-02**該当環境（メモリ128GB以上）では、上記のワーカー数上限がメモリではなくCPUコア数で決まるようになる。

```
  必要メモリ = 880MB × 並列数

  並列12（CPUコア数÷2の目安）→ 10.4GB   ← 192GBの5%程度。余裕
  並列24（全コア）           → 21.1GB   ← それでも余裕。ボトルネックはCPUコア数に移る
```

**REQ-PERF-04**: 128GB以上のメモリを検出した場合、既定ワーカー数を「物理コア数 − 2」（OS・レビューUI用に2コア残す）に引き上げる。ただし §9.3②の拡張構成でローカルVLM（§9.5）を同時常駐させる場合は、そのモデルの占有メモリ（40GB程度）を差し引いた残り容量で計算すること。

> 💡 **[学習メモ]** メモリが潤沢でも、並列数を無限に上げてよいわけではありません。CPUコア数を超えて並列化しても、OSがスレッドを切り替えるコスト（コンテキストスイッチ）が増えるだけで速くなりません。**「並列数の上限は、メモリ・CPU・外部APIのレート制限のうち、最も厳しい制約で決まる」**と覚えてください（本仕様では Mathpix のレート制限が実質的な天井になりやすい）。

### 16.1 ストレージ見積もり（320ページの本1冊）

**REQ-NFR-02（訂正）**: §8.2 REQ-PRE-01「各工程の出力を保存」は、**P1〜P10すべてを恒久的に保持する**という意味ではない。
既定では**直近の完了済み工程の出力のみ**をローリング保持し、次の工程が成功したら前段の出力を破棄する

|---|---|---|---|
| 撮影原本（HEIF Max 48MP） | 約 5 MB | **1.6 GB** | 恒久（元データ） |
| 撮影原本（ProRAW Max）※非推奨 | 約 80 MB | **25.6 GB** ← 現実的でない | — |

**1冊あたりの実運用時の必要容量（既定設定）**: 1.6GB（原本）+ 3.2GB（中間・処理中のみ）+ 256MB + 15MB ≒ **約5.1GB**（処理完了後、中間PNGを`tscan clean`で削除すると恒久的には約1.9GBまで縮小）

**REQ-NFR-02**: 中間PNGは既定で「直近1段階のみ」保持し、`tscan clean {book_id}` で一括削除できること。全段階保持は明示オプション時のみ。

## 18. テスト計画

| 種別 | 対象 | 手法 |
|---|---|---|
| 単体テスト | `detect_page_gaps`, `check_brace_balance`, `combine_confidence`, `insert_between`, `compute_display_page_index` 等の純粋関数 | `pytest` でテーブル駆動テスト |
| 画像処理テスト | 前処理（台形補正・デスキュー） | **合成画像**で検証（正解が既知の画像をわざと歪めて、戻せるか） |
| OCR回帰テスト | 固定の80ページ評価セット | CER と数式正解率を毎回測定し、**前回より悪化したらCI失敗** |
| 統合テスト | ingest → export の全経路 | 5ページのミニ本で end-to-end |
| **ページ管理テスト**（§7.7） | 挿入・削除・並べ替え後の整合性 | 320ページ処理済みの本に1ページ挿入し、**挿入した1ページ以外のimage_path・review_status・edited_atが一切変化しないこと**をアサート（M7の自動テスト版） |
| **UI手動修正テスト**（§11.7） | 個別ページ編集画面での書き換え | 高信頼度で自動採用済みのブロックをAPI経由で編集し、`edited_by="user"`が記録されること、Markdown/PDF再生成に反映されることを確認 |
| 性能テスト | 320ページバッチ | 実測時間・メモリ最大使用量を記録 |

```python
# 単体テストの例（テーブル駆動）
import pytest
from tscan.verify import check_brace_balance

@pytest.mark.parametrize("latex, expected", [
    (r"\frac{1}{2}",        True),
    (r"\frac{1}{2",         False),   # 閉じ忘れ
    (r"\frac{1}}{2}",       False),   # 閉じすぎ
    (r"\{ x \}",            True),    # エスケープされた括弧は対象外
    (r"x^{2}_{i}",          True),
    (r"",                   True),    # 空文字は正常扱い
])
def test_check_brace_balance(latex: str, expected: bool):
    assert check_brace_balance(latex) is expected
```

💡 **[学習メモ] `@pytest.mark.parametrize` とテーブル駆動テスト**
同じテストを入力だけ変えて何回も実行したいとき、`if` を並べたり
テスト関数を6個書いたりする必要はありません。
`parametrize` に `(入力, 期待値)` のリストを渡すと、
**pytest が6個の独立したテストとして実行**してくれます。

```
  test_check_brace_balance[\frac{1}{2}-True]   PASSED
  test_check_brace_balance[\frac{1}{2-False]   PASSED
  ...
```

どのケースが落ちたか一目でわかるのが利点です。
また、`r"\frac{1}{2}"` の先頭の `r` は **raw文字列**で、
「バックスラッシュをエスケープ記号として解釈しない」という意味です。
LaTeX は `\` だらけなので、**LaTeXを書くときは必ず `r"..."` を使う**と覚えてください。

```python
"\frac"     # → \f が改ページ文字(0x0C)と解釈されて壊れる 💥
r"\frac"    # → そのまま \frac  ✅
```

## 付録A. このプロジェクトで使う Python の概念マップ

初心者が本仕様を実装するうえで、どの概念がどこで必要になるかの地図です。

```
  【基礎】                    【本仕様での出番】
  ─────────────────────────────────────────────────────
  f-string `f"{x:04d}"`   ──▶ ファイル名の0埋め連番（§7.3）
  pathlib.Path            ──▶ ファイル操作すべて（os.path より安全）
  list / dict / set       ──▶ 誤読ペアの照合（set の積集合, §11.5）
  内包表記 [x for x in..] ──▶ 領域のフィルタリング
  lambda / sorted(key=)   ──▶ 読み順ソート（§10.3）
  try / except            ──▶ 1ページの失敗で止めない（§16.3）
  dataclass               ──▶ OcrLine, Block（§9.6, §12.2）
  Enum                    ──▶ BlockKind（§12.2）
  Protocol（型）           ──▶ エンジン差し替え（§9.6）
  @property               ──▶ needs_review（§12.2）
  型ヒント `list[int|None]`──▶ 全関数（エディタが誤りを指摘してくれる）
  ─────────────────────────────────────────────────────
  【ライブラリ】
  numpy 配列 / axis       ──▶ 画像 = 数字の表（§8.3, §8.4）
  OpenCV                  ──▶ 前処理すべて（§8）
  SymPy                   ──▶ 数式の意味検証（§11.5）
  FastAPI                 ──▶ レビューUI（§11.7）
  pytest parametrize      ──▶ テスト（§18）
  multiprocessing         ──▶ 並列化（§15.1）
```

### 学習の推奨順序

```
  Step 1: pathlib + f-string で「リネームするだけ」のスクリプトを作る（§7.6）
            ↓ ここで「動くもの」ができる喜びを得る
  Step 2: OpenCV で1枚の画像を読み込み、グレースケールにして保存する
            ↓ numpy の shape と axis に慣れる
  Step 3: Apple Vision で1枚をOCRして、テキストを標準出力する
            ↓ 外部エンジンの呼び方を覚える
  Step 4: dataclass で OcrLine を定義し、結果をJSONに保存する
            ↓ 「型を先に決める」設計に慣れる
  Step 5: 2エンジンの結果を difflib で比較する（§11.2）
            ↓ ここで初めて「品質保証」が実感できる
  Step 6: 10ページをループで回す → 例外処理の必要性を体感する
            ↓ try/except が「なぜ必要か」が腑に落ちる
  Step 7: 並列化・レビューUI・PDF出力へ
```

> **重要**: Step 1 から順に、**毎ステップで「動くもの」を作る**こと。
> 仕様書を全部実装してから動かそうとすると、どこが悪いか永遠に分かりません。
> これは §5.1 で述べたパイプライン設計と同じ思想です ―
> **小さく分けて、それぞれを確かめながら進む。**
